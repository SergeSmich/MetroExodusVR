## 2. Что выложено

### 2.1 `tools/caption_font_hook.py`

Пещера, вынесенная из 0.9.0-скрипта и параметризованная:

* `build_caption_font_hook(blob_rva, site_rva, font_name, prop_name, write=..., displaced=...)`
  → `(blob, site_patch, marker_off, dlen, code_len)`;
* `SETPROP_RVA_091 = 0x9F0D0`, `SETPROP_RVA_090 = 0x9BC70`;
* `derive_displaced()` читает смещаемые байты из самой DLL и проверяет, что это
  только `push reg` длиной 5..8; `pops_for()` строит симметричные `pop`.

`--self-test` дизассемблирует всю пещеру капстоуном и проверяет:

```
ok   0.9.1 font_name write=1: cave 11612 B (code 2672 B), site patch 8 B, marker +0xd5c
ok   0.9.1 font_name write=0: cave 11484 B (code 2544 B), site patch 8 B, marker +0xcdc
ok   0.9.1 override_font_name write=1: cave 11621 B (code 2672 B), site patch 8 B, marker +0xd65
ok   0.9.1 override_font_name write=0: cave 11493 B (code 2544 B), site patch 8 B, marker +0xce5
ok   0.9.0 font_name write=1: cave 11612 B (code 2672 B), site patch 6 B, marker +0xd5c
...
self-test: PASS
```

Проверки: каждый байт кода декодируется; **0** инструкций, начинающихся на
`00 00` (это ваш критерий 3, причина — `mov qword [reg+disp32], imm32`
собиралась с восемью нулями вместо четырёх, `4ac6565`); все ветки и все
RIP-relative ссылки бьют внутрь блоба; последняя инструкция — `jmp` на
`site + dlen`.

## 3. `font_name` против `override_font_name`: числа решают

| прогон | свойство | результат |
|---|---|---|
| **L-0026** (0.9.0, bag7) | `font_name` | `found_any=206`, `set_ok_any=206` из 209 совпавших: запись есть, сеттер записал |
| **L-0029** (0.9.0, bag9) | `override_font_name` | `found_any=0`, `set_ok_any=0`, `last set_ok=0`: записи нет ни у одного контрола |

Плюс механика: сеттер `0x9bc70`/`0x9f0d0` **не создаёт** запись, он пишет только
в найденную (`cmp byte [rbx],1` по kind). Плюс L-0018: `+0x60` — dword-пакетная
ссылка (пустая = `0xFFFFFFFF`), а A-0030 показал `[control+0x60] = 0` на наших
подписях — то есть переопределение на них не задано вовсе.

**Вывод: `--caption-font menu --caption-prop font_name`.**
`override_font_name` оставлен флагом на случай класса контролов, у которого
такая запись есть, — но на подписях из нашего фильтра её нет, и L-0029 это
уже измерил.

## 4. Чем эта пещера отличается от bag6–bag9

1. **Вызывается тело сеттера, а не вход.** bag6–bag9 звали сам `0x9bc70`, то
   есть попадали в собственный хук: из-за этого счётчик (в) в L-0029 показал
   `count=209 == matched` — он посчитал **наши же** записи. Новый код зовёт
   `site + dlen`, поэтому `reentries` остаётся 0, а дамп после сборки — чистое
   измерение того, что ставит игра.
2. **ABI вызова.** Вызываемый затирает 32-байтовое теневое пространство своего
   вызывающего (урок bag12, L-0031), поэтому оба `string_view` лежат **выше**
   него — на `[rsp+0x20]` и `[rsp+0x30]`, а не в тени. `sub rsp,0x38` подобран
   так, чтобы `rsp` остался выровнен на 16 к моменту `call`.
3. **Смещённые байты не захардкажены.** Скрипт читает их из DLL, требует 5..8
   байт и только `push reg`, и в эпилоге проигрывает ровно прочитанное. Для
   0.9.1 ждутся 8 байт (`40 53 55 57 41 56 41 57`), для 0.9.0 — 6
   (`40 53 55 57 41 56`). Если реальность другая — сборка упадёт с печатью
   фактических байт, а не соберёт DLL со сдвинутым стеком.
4. **Счётчики записи вынесены из ветки `found`:** `+0x1C70` `set_calls`,
   `+0x1C74` `set_ok`, `+0x1C78` `set_fail`, `+0x1C7C` `set_last` (сырой `al`).
   Ровно про L-0029 §2: там `set_ok_any` инкрементился только внутри `found`,
   и успех без существующей записи был бы невидим. Маркер 0x2000 байт, поля
   далеко за последним полем bag15 (`+0x1C6C`).
5. **`imm64/imm32`**: ваш фикс из `4ac6565` сохранён; больше того — теперь он
   проверяется автоматически (§2.1, проверка на `00 00`).
6. Сохранён весь bag15-инструмент (рабочий `local_text`, сканы bag/handles,
   проба резолвера `res_menu/res_arial/res_regular`), ничего не выброшено.

## 6. Валидаторы и где первый запуск может упереться

L-0033 доказал, что проверки `0x20..0x7E` на нашем пути не исполняются: они
читают исходные ASCII-литералы в `.rdata`. Значит патч `0x5e → 0xff` ничего не
меняет. В проверенном `cand-bytecmap` он был, поэтому по умолчанию я его
**оставляю** (разница с проверенным кандидатом тогда ровно одна: кодировка +
шрифт), а `--no-validators` его убирает. Скажите, если нужен другой дефолт.

Ожидаемые точки отказа первого запуска, по порядку вероятности:

1. `caption font: setter 0x9f0d0 starts with …, expected …` — пролог не тот.
   Скрипт напечатает фактические байты; дальше `--site-head <hex>`.
2. `not a known caption address` / `expected X, found Y` — RVAC в
   `strings-0.9.1.tsv` не совпадают с DLL (переснять планом).
3. `cannot find size/capacity pair` на inline-сайтах — нет `funcs-0.9.1.json`;
   сначала попробуйте без него (окно с ресинхронизацией), потом дайте карту.
4. `ui2 … cannot map slot` — жду базы UI2.

## 7. Фильтр подписей надо пересобрать

Фильтр в хуке считает `fnv1a32(байты значения)`, то есть хэш от **нашего
пейлоада**. `ru/caption_filter.json` построен от 0.9.0-текстов
(`encoded_with: tools/apply_ru.py encode_text`). Если переводы 0.9.1 хоть в
одной строке отличаются, эти подписи шрифт не получат — молча.

```
python tools/apply_ru_091.py --strings ru/strings-0.9.1.tsv --build-filter ru/caption_filter.json
```

На сборке скрипт печатает `ok caption filter: all N translated captions are
covered` либо предупреждение с числом непокрытых и их хэшами. Сейчас, на
0.9.0-таблице: `all 176 translated captions are covered` — то есть функция хэша
совпадает с той, что вшита в пещеру.

## 8. Порядок прогонов (предложение)

**Прогон 0 — пещера на стоковом DLL, без перевода:**

```
python tools/apply_ru_091.py --src <0.9.1 orig> --out build/cand-hookonly.dll \
       --hook-only --caption-font menu --verify
```

Строки английские, меняется только 8 байт на `0x9F0D0` да новая секция. Что
даёт: живой `set_calls / set_ok / set_fail` и отсутствие краша — до того, как
мы тратим прогон на полную сборку. Если `set_calls` растёт, а `set_ok = 0`,
значит шрифт не пишется, и искать надо не в кодировке.

**Прогон 1 — полная сборка:**

```
python tools/apply_ru_091.py --src <0.9.1 orig> --out build/cand-charmap-menu.dll \
       --caption-font menu --caption-prop font_name --verify
```

Снять из маркера (RVA печатается): `calls / caption / matched`,
`set_calls / set_ok / set_fail / set_last`, `found_any / set_ok_any`,
`cap_fn_len / cap_fn_16`, `val_text_len / val_text_16`,
`res_menu / res_regular / res_arial`, `qword [c+0x60]`.

**Если `set_ok > 0`, а кириллицы нет** — тогда либо менеджер не резолвит
`menu` (`res_menu = 0`, берём `regular`: он в живых дампах ненулевой, L-0030,
и покрывает перевод на 99.0 %), либо `font_name` декоративен — и тогда нужен
bag16 из A-0031 (байты рабочей подписи), чтобы отличить «не тот шрифт» от
«не та кодировка» и от «рисует другой элемент».
