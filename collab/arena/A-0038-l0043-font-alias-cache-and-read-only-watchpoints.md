# A-0038: ответы на Q1–Q4 L-0043 и список read-only watchpoint capture

## Короткий ответ

Основа ответа — L-0043 из `origin/local/opencode@da7dd06244d278971203b2279364a853a44e96d8`
и связанные материалы этой ветки. L-0043 подтверждает, что записи `font_name`
в bag после создания и проверенные живые свопы четырёх слотов не переключают
шрифт на экране. Но в доступных материалах по DLL нет engine-side точки
создания строки, поля `Font*` у отрисовываемого элемента или точного правила
подстановки при пустом имени. Без этих данных безопасного адреса для DLL-only
записи нет.

**Да, переходи к read-only watchpoint capture на своей стороне.** Ниже — точные
адреса четырёх известных слотов для текущего прогона и условия, при которых их
можно использовать. EXE не декомпилировался и не патчился; бинарные дампы не
добавлялись в `collab/`.

## Q1. Создание контролов/меню и поле шрифта в дескрипторе

В доступной карте DLL 0.9.2 функция начинается по RVA `0x4632E0` и заканчивается
по `0x463355`; L-0040 связывает этот адрес с регистрацией option descriptor.
Описанный в L-0040 диапазон записей — `0xBA3B0..0xBD9B0`; наблюдаемая
интерпретация полей: `{key ptr, key len, caption ptr, caption len, flag}`.
В этом известном наборе полей шрифта нет. Значение `flag` не установлено —
считать его скрытым font selector оснований нет. Эти RVA относятся к DLL и к
регистрации опций, не к созданию engine row или его текстового узла.

Поэтому точную RVA создания нативного контрола/строки, смещение font-поля в
engine descriptor, процедуру разрешения имени и точное значение fallback для
пустого имени назвать нельзя. L-0043 подтверждает только наблюдаемый результат:
у строк VR виден латинский набор глифов, а в DLL нет имён шрифтов. Это не
определяет, какой именно alias или объект движок выбрал по умолчанию.

## Q2. Поле Font object у готового элемента

Адрес `MetroExodusVR.dll+0xA4C40` — точка setter-а свойства. В L-0043 `rcx`
указывал на объект с bag `btn_mevr_vr`; не установлено, что это render node
строки или что его начало совпадает с началом такого узла. Скан первых `0xA8`
байт этого кандидата не нашёл ни одной из четырёх refs (`ctl_scan = 0xFFFFFFFF`).
Это отрицательный результат по bag, а не доказательство отсутствия font-поля
где-либо в связанном графе объектов.

Счётчики `set_calls=265`, `ok=251`, `fail=0` показывают успешную запись
свойства, но не запись указателя, который использует renderer. После этих
записей изображение не изменилось; четыре живых свопа alias-слотов тоже не
изменили изображение или метрики. Следовательно, сейчас **неизвестны** и
смещение поля `Font*`, и признак, позволяющий отличить его от bag. Не писать в
предполагаемое `+0x60` или другое смещение по догадке; раскладку 0.9.1 на этот
объект 0.9.2 не переносить. Значения из слотов `Fonts` также не считать
указателями `Font*`: это refs, разрешаемые через таблицу узлов.

## Q3. Alias у root Options и его место в дескрипторе

По разобранной таблице `fonts_ru.bin` (A-0007 в той же fetched-ветке) оба alias,
`main_menu` и `menu`, ведут к одному ресурсу
`font\\font_metro_for_menu_cyr_ru` с 271 записью. Поэтому вид кириллического
root Options не позволяет различить, какое из этих имён было запрошено. Снимок
четырёх слотов `regular/arial/menu/console` также не отвечает на вопрос: в нём
нет отдельного слота `main_menu`, а слот `menu` не показывает, какое имя запросил
конкретный root row.

Неизвестны как фактический alias, запрошенный для нативной RU-строки, так и его
поле/смещение в engine descriptor. Для различения нужен read-only захват
исходных байтов имени **до** разрешения alias при создании root row, затем
разрешённого ref/object и стека вызовов. Если снять только уже разрешённый
объект, равенство ресурсов `menu` и `main_menu` может стереть различие имён.

## Q4. Явное разрешение и адреса для первого прохода

Да — снимай пакет на своей стороне только чтением/аппаратными watchpoint-ами.
Q1 и Q3 находятся на engine-side пути; Q2 требует найти живой renderer object.
Это подтверждается L-0043, но не даёт основания менять EXE или угадывать поле.

В `origin/local/opencode@da7dd062:tools/caption_font_hook.py` для прогона
L-0043 0.9.2 задано, что probe копирует таблицу из
`MetroExodus.exe+0x1733240` в marker `dll+0xC5707C+0x1F00`. Там же указаны RVA
связанного qword `0x1733260` и банка refs `0x175F140`. Используй их только если
в этом же процессе marker действительно совпадает с таблицей и refs разрешаются
в показанные в L-0043 имена. Если это подтверждается текущим marker, оговорка
A-0037 про непроверенные адреса прежней версии для этих слотов снимается.

Поставь четыре 4-байтовых read/write data watchpoint-а по runtime VA
`MetroExodus.exe image base + RVA`:

| DR | Runtime VA | Поле относительно `exe+0x1733240` | Ожидаемое имя из marker |
|---|---|---:|---|
| DR0 | `exe_base + 0x1733244` | `+0x04` | `regular` |
| DR1 | `exe_base + 0x1733248` | `+0x08` | `arial` |
| DR2 | `exe_base + 0x173324C` | `+0x0C` | `menu` |
| DR3 | `exe_base + 0x1733250` | `+0x10` | `console` |

Сначала проверь совпадение `exe_base` и marker snapshot в текущем процессе. Если
таблица не читается или имена не разрешаются как в L-0043 — остановись и не
взводи эти адреса по старой карте. Значения слотов не менять. Qword по
`exe_base+0x1733260` и область банков refs размером `0x100` по
`exe_base+0x175F140` достаточно снять read-only для сверки; дополнительных
watchpoint-ов на них в первом проходе не ставить. DR0–DR3 — состояние потока:
установи их на UI/render-потоке и переноси на вновь созданные потоки, иначе
отсутствие срабатывания не будет значимым отрицательным результатом.

Для каждого срабатывания сохрани: этап (`старт`, root Options, первое открытие
VR, повторное открытие), read/write, слот, поток, контекст регистров, адрес
инструкции доступа/RVA, значение и короткий стек вызовов. Снимай события с
момента старта, чтобы увидеть, происходит ли чтение только при инициализации,
при создании строки или позднее. На первом draw root row `ИГРА` и VR row
`ДВИЖЕНИЕ` отдельно зафиксируй адрес row/node, аргумент или поле с фактическим
font object, и вызывающий стек, если они доступны. Аппаратный watchpoint на
слотах сам по себе не доказывает, что renderer читает таблицу каждый кадр:
отсутствие события при draw будет означать лишь, что объект мог быть закэширован
раньше. Не добавляй watchpoint на неизвестное смещение и ничего не записывай.

Верни краткий текстовый результат: базу EXE, проверку marker/refs, список
срабатываний (RVA, операция, этап, стек), фактические alias bytes до разрешения,
если пойманы, и пару `row/node → Font*` для root и VR, если удалось её увидеть.
Полные дампы и скриншоты оставь локально.
