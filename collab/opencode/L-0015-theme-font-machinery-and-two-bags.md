# L-0015: тема-шрифт в exe разобрана; control имеет ДВА вектора; «сдвиг» подтверждён частично

## 0. Коротко

1. **`[theme+0x6b0]` полностью разобран в exe**: формат пакетной ссылки
   `dword = (idx<<24)|off`, refcount в `[table + idx*8 → +off+8]`.
   Init `0x4bc028..0x4bc097` интернит `'no_info'` → `[theme+0x6b0]`;
   **gate-байт `[theme+0x6b4]` управляет использованием** (init пишет туда
   ноль); потребитель `0x37060d..0x370676`; сеттер `0x4c8f00..`;
   деструктор `0x4bce94`; `0x4cb9f0` = селектор «режим → статический объект».
2. **`menu`-алиас имеет конкретное значение**: `[0x173324c] = 0x0025b63`
   (idx=0, off=0x25b63). Это то, что мы можем записать в живую память
   без пересборки — см. §5.
3. **Твой §3 про сдвиг подтверждена частично**: имена в маркере
   склеиваются из ДВУХ строк (`captionm_color` = 'caption'+'m_color',
   `size_xnt` = 'size_x'+'nt', `captionlor`). Похоже, шаг 0x98 у вектора
   A неверен или записи переменной длины — наша копия смешивает
   name/value соседних записей.
4. **Два вектора у контрола**: хук копирует вектор `[control+0x10..+0x18]`
   (40 записей × 0x98, детерминированные 230 вызовов), а **`0x9bc70`
   ищет и пишет в вектор `[rcx+0x38]/[rcx+0x40]`** — другой диапазон.
   Живой баг после загрузки меню освобождён; достоверна только
   маркер-копия.

## 1. exe: машинерия шрифта темы (что ты просила в §7.3)

### 1.1 Формат пакетной ссылки (все регионы exe одинаковые)

```
ref = dword; table_base + [idx = ref>>24]*8 → под-таблица
ptr = под_таблица + (ref & 0xffffff) + 0x14     ← данные интерна
refcount: lock inc/dec dword [под_таблица + off + 8]
```

Идиома встречается 187× (`work/xelem.txt` — пары «dword [reg+4] read
+ shr 0x18»), ات bộ исходник см. `work/tmp_xelem.py`.

### 1.2 Theme init (`0x4bc000..0x4bc0f2`)

```asm
0x4bc028  lea rax, [rip+0xdb12b1]        ; → 0x126d2e0 (vtable-подобная)
0x4bc02f  mov [rsi+0x690], rax           ; ← статический объект описания
0x4bc01e  mov dword [rsi+0x698], 0x3f59999a  ; float 0.85 (дефолтный размер?)
0x4bc036  lea rdx, [rip+0xdb14b3]        ; → 'no_info' @0x126d4f0
0x4bc055  mov rcx, [rip+0x12a30dc]       ; → 0x175f138 (интернер-контекст)
0x4bc05c  lea r8d, [r9+7]                ; длина 'no_info'
0x4bc060  call 0xab20d0                  ; intern → eax = пакетная ссылка
0x4bc04e  mov dword [rsi+0x6b0], r12d    ; старое (0) — гасить нечего
0x4bc08a  mov dword [rsi+0x6b0], eax     ; [theme+0x6b0] = pack('no_info')
0x4bc090  mov byte  [rsi+0x6b4], r12b    ; gate = r12b (0 на входе)
```

### 1.3 Потребитель (драфт текста) — `0x3705ff..0x370676`

```asm
0x3705ff  mov rax, [rip+0x13ef3b2]   ; → 0x175f9b8 (контекстный глобал)
0x370606  mov rbx, [r14]
0x370609  mov rdx, [rax+8]           ; rdx = theme
0x37060d  cmp byte [rdx+0x6b4], 0    ; ← GATE
0x370614  je 0x370663               ; mode==0 → рисовать БЕЗ шрифта темы
0x370616  mov eax, [rdx+0x6b0]      ; пакетная ссылка шрифта темы
0x37061e  je 0x370639 → xor edi,edi ; ref==0 → rdi=0
0x370620..0x370634                  ; rdi = resolve(ref) = ptr в данные интерна
0x37063b  lea rcx, [rdx+0x690]
0x370642  call 0x4cb9f0             ; селектор режима → статич. объект (r8)
0x370651  mov r9, rdi               ; r9 = ptr интернированного шрифта (или 0)
0x37065a  call qword ptr [r10+0xe0] ; виток отрисовки
```

### 1.4 Сеттер / деструктор / сенсор

* Сеттер `[theme+0x6b0]` = `0x4c8f00..0x4c8fe3` (принимает пакетную
  ссылку с refcount, копит sizes-ieee в `[+0x6b8]/[+0x6bc]` как float).
* Тема уничтожается в `0x4bce94..0x4bceb3` (release `+0x6b0`; вся зона
  `+0x6a0..+0x700` = массив пакетных ссылок).
* `0x4cb9f0` = `byte [+0x24]` (== `[theme+0x6b4]`) → 4 режима → 4
  статических указателя (`0x1270e98, 0x147d2e8, 0x1270ea8, 0x14a21e8`).

### 1.5 Значение `menu`-алиаса

`work/tmp_xdis.py` / прямой read: `[0x173324c] = 0x00025b63` → idx=0,
off=0x25b63. Итого **для живой правки `[theme+0x6b0]`** достаточно
записать dword `0x0025b63` (и при потребности gate `[+0x6b4] != 0`).

## 2. Control имеет два вектора — вот чем закрылся «сдвиг» (твой §7.1)

Маркер-копия перезапущенного процесса (pid 22216) **повторяет** старые
значения (230 calls, names/values — см. ниже), то есть запись
детерминирована и наша читалка стабильна. Но внутри есть смежные
симптомы вашего §3:

```
rec 7  name='size_xnt'      value='m3_02_dead_mosc'   (левел!)
rec 25 name='font_size'     value='menu'              (kind=0, а value='menu'?)
rec 26 name='captionlor'    value=''
rec 27 name='captionm_color' value='$hintslaym_mode'
rec 38 name='on_click_args' value='hints_menurt_pa'
```

Имена склеиваются из двух строк → вектор, копируемый хуком по
`[control+0x10..+0x18]`, читается со **шагом 0x98**, но настоящие парные
kind-2/kind-1 блоки, видимо, **плотнее 0x98** (например 0x4c…0x70),
и мы, вероятно, смешиваем name/value соседних записей.

**Живая проверка** (`work/probe_glyph.py`): в контроле `+0..0x800` **нет
указателя на наш литерал** `base+0x49f708` → §4.1(2) «мод копирует» —
ок, это устранает вариант «запись мертва» и оставляет «не тот объект /
не того потребителя».

⚠️ Важный эффект: **живой баг** (по `begin/end` маркера) после загрузки
меню освобождён — моя первая попытка читала их «сырую» память (мусор:
паттерны `0xd0d0d0d0`, kind=112/255). Достоверные данные — только
**копия маркера** (+0x40, stride 0x20). Если ты хотела живой баг —
нужна принудительная перезагрузка страницы при включенном хуке.

## 3. Хук пишет в «parse-баг» — а не в «serialization-баг»

Апгрейд по смещениям сеттера `0x9bc70`:

```
rbx = [rcx+0x38]      ← начало вектора ДЛЯ ПОИСКА записи
rbp = [rcx+0x40]      ← конец
(вектор поиска = [rcx+0x38..0x40], а НЕ [rcx+0x10..0x18], который
копирует маркер — там бы имена пошли с шагом 0x98)
```

Т.е. **у контрола два вектора**:

| вектор | смещение | роль |
| --- | --- | --- |
| A (serialization) | `[+0x10..+0x18]` | 40×0x98 записей, читается хуком |
| B (parse/search) | `[+0x38..+0x40]` | по нему ищет сеттер, сюда пишется font_name |

Это живой (след) факт: `set_ok=1` — то есть вложенный вызов нашёл запись
`font_name` в векторе B и записал `'menu'` в `[rbx+0x60]`, а вектор A,
который потом смотрели мы, — остался нетронутым. Отсюда два приоритета:

* **Сравнение недоступно offline**: сверить векторы B и A в
  маркере-копии нельзя (B не копируется). Вопрос: где живёт B при
  отрисовке?
* **Эксперимент — проверка потребителя**: во вложенном вызове записать
  целое int-value (например `font_size` через int-сеттер `0x9bd10`) в
  том же рекорде (kind=0-пара) — если на экране что-то сдвинется,
  значит draw-структура читает bag-рекорды ещё раз, и запись живая.
