# L-0024: прогон bag7 — `matched=209`, но у последнего совпадения `font_name` в баге НЕТ

## 0. Числа (сборка до фикса `gate`, A-0023)

```
calls=1204  caption=259  matched=209       <-- фильтр работает
set_ok=0  found=0  kind=0  has_kind2=0
last caption len=9  sample=b';?7I:h\x01x'  (похоже на charmap-байты, не мусор)
gate=[rbx-0x54]  (невалиден по A-0023) qword [c+0x60]=0
control=0x9af9dfef60  bag=9 записей
```

Баг последнего совпавшего контрола (полный дамп):

```
0 kind=2 caption   1 kind=1 caption
2 kind=2 hint      3 kind=1 hint
4 kind=2 img       5 kind=1 img
...
```

**Ни `font_name`, ни `override_font_name` в нём нет.** Поэтому сеттер
`0x9bc70` честно вернул 0 — записывать было некуда.

## 1. Что это значит

1. **Фильтр работает**: 209 совпадений из 259 caption — это наши строки.
   Прогон действителен (A-0021 §2, третья строка таблицы).
2. **Контрол, на который мод ставит `caption`, может не иметь
   `font_name` вовсе** — его баг это минимальный набор (caption/hint/img).
   Тогда `font_name` на элементе писать некуда, и путь «через свойство
   элемента» упирается в отсутствие записи.
3. Логично, что **текст рисует другой элемент** (например, дочерний
   text-элемент), а `caption` вешают на контейнер/кнопку. Это совпадает
   с твоим §5 (A-0021): наши подписи рисуются не шрифтом того контрола,
   у которого стоит `font_name`.

## 2. Следующая сборка (уже собрана, ждёт перезапуска)

1. **`gate` исправлен**: `movzx eax, byte [rbx+0xac]` (disp32), дизасм
   `0xc27f38` показывает `[rbx + 0xac]`.
2. **Агрегаты по всем совпавшим** (в хвосте маркера):
   `+0x1900 found_any`, `+0x1904 set_ok_any`,
   `+0x1908 первый контрол с найденной записью`, `+0x1910 его q60`.
   Маркер RVA: **`0xc282d5`**.
   Это ответит на главный вопрос: **у скольких из 209 баг содержит
   `font_name`** и сработала ли запись хоть раз.

## 3. Вопросы к тебе

1. Если `found_any` окажется **0** — подтверждаешь, что свойство
   `font_name` на элементе мёртво для нашего пути, и остаётся путь B
   (`+0x60`/тема)?
2. Если `found_any > 0`, а `set_ok_any` тоже > 0, но вид не изменился —
   это твоя ветка «font_name декоративен»; тогда идём в `+0x60`.
3. Есть ли смысл в этой же сборке писать `font_name` **и**
   `override_font_name` (оба), чтобы покрыть контролы, у которых есть

## 4. Визуально (ответ пользователя)

Пользователь прислал два скриншота VR:

* **правая колонка значений игры — правильная кириллица**: `ВЫКЛ`,
  `ВКЛ`, `НАЗАД`, `?КНЕЗ?` (значения рисуются charmap-шрифтом);
* **левые подписи (наши переводы) — битые charmap-байты**:
  `;?75<@5L5;L;?71:HX`, `7DCI?<H57?7?OD3N`, `7;;U<D:IPL3?I7DCI?` и т.д.

Это независимое подтверждение §5 A-0021: **наши подписи и игровые
значения рисуются разными шрифтами**. Наш шрифт — не charmap
(байты показываются как кодпоинты), шрифт значений — charmap.

Важное следствие: тест `typewriter` на этом прогоне фактически не
дошёл до отрисовки — у последнего совпавшего контрола записи
`font_name` нет (`found=0`), запись пропущена. Нужны агрегаты
`found_any/set_ok_any` (§2), чтобы узнать, сработала ли запись хоть у
одного из 209.

`FSR/DLSS/TAA` на скриншотах не видны — пользователь ещё не подтвердил
страницу апскейлинга.
