## 2. Почему `U+0410` не тот кодпоинт

Из `ru/ENCODING_NOTES.md` §7 (замеры 0.9.0, подтверждены дважды):

| Шрифт | записей `tcmap` | глифов | ≥ `0x80` |
|---|---|---|---|
| `arial` (RU = US побайтово) | 256 | 95 | **0** |
| `menu`/`main_menu` (RU) | 271 | 238 | 111 |

* `arial` — тождественная таблица: запись `i` = кодпоинт `i`. Значит
  рендер не декодирует ни CP1251, ни UTF-8 — он берёт байт как кодпоинт
  (или таблица `menu` — индекс charmap'а, но это другой шрифт).
* Отсюда `DOH5` вместо `ИГРА` и пустая проба `0x80..0xFF`: у `arial` там
  нет ни одного глифа.
* Следствие для кита: CP1251-байт `0xC0` ищется как U+00C0. Если положить
  кириллицу в U+0410, она недостижима. Если положить её в `0xC0..0xFF`
  (как в `cand-bytecmap.dll`) — достижима при том же рендере, без единой
  правки кода и без смены `font_name`.

Проверка гипотезы бинарная и дешёвая: один VR-прогон `cand-bytecmap.dll`
против такого же прогона обычного `cand` из README. Если кириллица
появится только в первом — рендер точно byte-as-codepoint, и тогда
`merge_cyrillic.py` надо чинить именно так (п.3).

## 3. Правка кита (один файл, ~20 строк)

В `merge_cyrillic.py` после вливания `U+0400..U+045F` добавить второй проход:

```python
# для каждого байта >= 0x80, который реально встречается в переведённых
# строках после cp1251: cmap[b] = глиф донора для chr(cp1251[b])
for b in used_bytes_ge_0x80:
    ch = bytes([b]).decode("cp1251")
    if ord(ch) < 0x100:        # NBSP, °, №... — не трогаем
        continue
    gname = add_outline(donor, ch)   # как сейчас для U+04xx
    for table in unicode_cmap_tables:
        table.cmap[b] = gname
```

Готовый постпроцессор уже написан: `work/remap_cyr_latin1.py`
(`--fonts <dir> --donor C:\Windows\Fonts\arial.ttf`), 112 записей на шрифт,
после сохранения перечитывает cmap и падает, если запись потерялась.
