# Кодировка текста мода: текущее состояние разбора

Документ фиксирует, что уже доказано и где именно застряла локализация.
Нативные строки игры переводятся и отображаются корректно; проблема — только
у строк, которые рисует сам мод.

**Актуальность:** разделы 1–8 содержат результаты ранних прогонов. Для страницы
VR в сборке 0.9.2 используй более новые наблюдения в §11: старое обобщение про
один US-шрифт для всех подписей мода больше не считать установленным фактом.

## Что работает

* Перевод применяется к бинарному релизу: в PE добавляется секция `.ru`
  (RVA `0xbcc000`), сайты `lea reg,[rip+literal]` перенаправляются на новые
  строки, inline `std::string` заменяются `jmp`-стабами.
* ASCII-валидаторы ослаблены (`cmp al,0x5e` -> `cmp al,0xff`):
  `0xa1816`, `0xa30f6`, `0xa12c8`, `0xa12c6`.
* Установка пишет бэкапы `.orig` и пиннит версию: `updater.json`
  (`mode=never`, `pinned_version=0.9.0`).
* В игре строки действительно подменяются, нативные подписи
  (`НАЗАД`, `ВКЛ`, `Прокрутка`) остаются корректными во всех сборках.

## Что не работает

Байты, которые мод отдаёт в UI, интерпретируются таблицей, совпадающей с
**US-charmap** (из `stable_us.lng`): 203 записи в порядке частоты глифов.

```
US[0x29]='D'  US[0x2c]='E'  US[0x35]='B'  US[0x45]='4'
US[0x37]='P'  US[0x40]='J'  US[0x50]='/'
```

Отсюда наблюдаемый мусор: `SNAP TURN ANGLE` -> `DBEF 4...`,
`ВКЛ` (индексы RU-charmap `0x37,0x40,0x50`) -> `PJ/`.
Кириллицы в US-charmap нет вообще; RU-charmap содержит 271 запись,
из них 67 кириллических (`RU[0x37]='В'`).

## Проверенные и отброшенные кодировки

| Кодировка | Результат в VR |
|---|---|
| CP1251 | пустые подписи, tofu в описаниях |
| UTF-8 | `.notdef` на каждый байт |
| `.lng` compact-индексы (`idx<0xE0` -> 1 байт, иначе `v=idx+0xDE41`, `b=v/255`, `r=v%255`) | латинский мусор по US-таблице |

## Карта кода

| RVA | Что это |
|---|---|
| `0x80ebf0` | глобал страницы VR-настроек |
| `0xb4290` | конструктор страницы |
| `0xb4cb0` | ленивый getter (вызывает билдер) |
| `0xb0b50` | билдер страницы (пишет записи `string_view`) |
| `0xb4d60`, `0xb7210` | потребители getter'а |
| `0x480540` | `lea rcx,[0x80ebf0]; jmp 0xb4290` (статический ctor) |
| `0x4c5648` | `GlyphAtlas` |
| `0x4c7360` | `text node draw` |
| `0x51a743` | `[links] no font resource {}; ImGui's own instead` |
| `0x18a7a0..0x18abcd` | glyph-хуки |

Записи страницы: `{key ptr/len @+0x00/+0x08, label ptr/len @+0x10/+0x18, ...}`;
строки создаются `0x2a8c0`/`0xa7d90`/`0xa7df0` **без конверсии кодировки**.

## Ранняя гипотеза (не подтверждена для 0.9.2)

До runtime-измерений из §11 предполагалось, что текст мода рисуется шрифтовым
ресурсом/атласом с US-charmap, а не через языковой путь локализации игры.
Эту гипотезу не переносить на страницу VR в 0.9.2. Ранние варианты фикса:

1. переключить ресурс/таблицу на RU-вариант и кодировать перевод индексами
   RU-charmap;
2. найти узкую->Unicode конверсию (таблица 256 codepoints,
   `MultiByteToWideChar`, глобальный charset) и заставить её декодировать
   наши байты;
3. пройти по wide-string пути.

## Ограничения патча

* inline `std::string`: длина <= `0xF` (SSO);
* `string_view`: <= `0x7E`; подпись 1..`0x3E`;
* общие литералы (`OFF`, `TAA`, `DLSS`, `FSR`) не трогаем — только
  редиректы в сайтах мода;
* ImGui-слой (метрики, отладка, dev-хоткеи) не переводится, кириллица в
  ImGui не требуется;
* файлы игры не изменяются — только `MetroExodusVR.dll`.

## 11. Механизм выбора шрифта для VR-подписей: статус по L-0043–L-0046

Этот раздел относится к runtime-измерениям страницы VR в 0.9.2. Он уточняет
ранние выводы выше, но не заменяет отсутствующий статический анализ движка.

### 11.1 Что показали новые измерения

По L-0046, в снятом процессе пара полей объекта подписи содержит ссылку на имя
шрифта и масштаб: `+0xC0` — имя, `+0xC4` — `float` масштаба. В этой выборке у
подписей страницы указан `regular` (ref `0x17056f48`, масштаб `0.039`), у
части меню — `menu` (ref `0x001c58b0`). Эти числовые refs привязаны к данному
процессу и не являются адресами для патча.

Цепочка `[obj+0xC8] → [style+0x58]` в том же отчёте разрешается в кириллические
ресурсы: для подписи — `font\\font_font_regular_cyr_ru`, для меню —
`font\\font_metro_for_menu_cyr_ru`. Это подтверждает содержимое метаданных и
путь разрешения ресурса в конкретном захвате, но не доказывает, что именно этот
ресурс/объект отдаёт глифы видимой строке.

Кадр по-прежнему показывает латиницу (`DOH5`, `OH5nD@5`). Поэтому выбор имени
в объекте и результат видимой отрисовки пока расходятся. Из имеющихся данных
нельзя назвать функцию, которая делает окончательный выбор, поле реального
рисующего `Font*`, место кэширования атласа или fallback в `MetroExodus.exe`.
Обнуление глифов в 31 найденном живом Font-объекте не изменило подпись; это
ограничивает вывод только этими 31 объектами и не доказывает, что атлас запечён
или что все возможные объекты были найдены.

В L-0046 также уточнено разрешение имён в текущем процессе: `regular` —
`0x17056f48`, `menu` — `0x001c58b0`, `main_menu` — `0x000d8450`,
`typewriter` — `0x00455b20`. Кандидат `arial` (`0x17056e30`) в этом обходе
дал длину `28781`, поэтому он не подтверждён как корректная запись имени.
Старые числовые refs и предположение «`menu` отсутствует, значит движок берёт
`arial`» не использовать как установленный факт.

### 11.2 Проверенные варианты, которые не исправили подписи

| Проверка | Результат и точная граница вывода |
|---|---|
| Другие байтовые кодировки как способ выбрать шрифт | Для этого пути работает charmap-байт; UTF-8 дал пустые подписи/неверные глифы, CP1251 также не дал кириллицу. Кодировка не переключает объект шрифта. «Latin-1» описывает вид части identity-вывода, но не доказывает отдельный декодер. |
| Перезапись `+0xC0` после создания строки | Кадр не менялся. Это закрывает такую запись как переключатель уже созданного объекта, но не устанавливает, что читает конструктор. |
| Живые подмены слотов таблицы `Fonts` после старта | Четыре проверенных подмены не изменили кадр. Это не доказывает, что таблица не читалась раньше и что объект не был кэширован при создании. |
| Обнуление глифов в найденных Font-объектах | В описанном L-0046 прогоне подпись не изменилась. Эти объекты не подтверждены как источник видимых глифов. |
| Встроенные TTF/ImGui мода как источник страницы Options | В прогоне L-0045 ImGui не инициализировался; эта ветка не объясняет нативную страницу Options в том прогоне. |

### 11.3 Неразрешённые поля и запрещённые догадки

* В L-0044 `+0x50` читается как имя контрола, `+0xD0` содержит две ссылки на
  текст; ни одно из этих наблюдений не делает их селектором шрифта. `+0xC0`
  содержит имя и масштаб, а `+0xC8` ведёт к объекту стиля. Семантика `+0x58`
  и `+0x60` для фактического рисующего объекта не установлена. Не писать в эти
  поля и не переносить разметку между разными типами объектов.
* Переименование alias в строку с суффиксом `_ru` не подтверждено как решение:
  alias `regular`/`menu` уже разрешаются в RU-ресурсы в таблице и цепочке,
  описанных L-0046. Имя ресурса и alias — разные уровни.
* Изменение `tcmap` без согласованного атласа не является проверенным путём.
  Кадровые опыты с найденными Font-объектами не показали, что эти таблицы
  владеют подписью.
* Подмена живого объекта подсказки `$back` не доказана. Одинаковая vtable,
  если она подтверждается для двух объектов, не устанавливает совместимость
  их полей, владения и масштаба; нужен текстовый результат сравнения
  `work/rec_diff.py`.
* Гипотеза о fallback на `arial`, загрузке `fonts_us.bin` для этой строки и
  конкретном читателе таблицы `exe+0x1733240` остаётся открытой. Имеющиеся
  runtime-данные не дают RVA или байтов инструкции; EXE здесь не анализировался
  и не патчился.

Для следующего шага нужны текстовые результаты чтения/сравнения объектов и
стека, снятые пользователем в его read-only прогоне. До установления точного
DLL-only места создания/переназначения и проверенных исходных байтов патч не
готовить.
