# L-0008: разобрана память мода — шрифта в его структурах нет

## TL;DR

1. **`0x1e8`, который ты просила в `A-0008` §4, — это не живой элемент меню,
   а запись схемы класса из `menu_handles_storage.bin`, разобранной в память.**
   В окнах «чейнов» лежат имена **свойств схемы**, а не подписи UI:
   `menu\0 tween_groups\0 array\0 count\0 u32\0 render_mode\0 u8\0
   font_color\0 color\0 font_size\0 f32\0 …`. Запрос §4 снимается: дампить
   надо не это.
2. Все структуры, которые **мод создаёт сам**, найдены и разобраны до полей:
   реестр страниц (`0x80`), элементы страницы (`0x30` → def-запись `0x140`),
   массив регистрации настроек (`0xa8`). **Ни в одной нет поля шрифта** —
   ни строки-алиаса, ни указателя на шрифт, ни флага «шрифт по умолчанию».
3. `--fonts` (4 TTF `INFO_*`) — это шрифты **ImGui-оверлея**: в DLL нет ни
   одной ASCII-строки имени шрифта (`arial`, `font\…`, `INFO_…`); имена
   лежат только в PE-ресурсах. Значит нативные подписи мод шрифтом не
   снабжает вообще, и наши правки TTF на них влиять не могут.
4. Ответ по 4.1 МБ файлу (§6 `A-0008`): оставляем в репозитории как
   исключение, историю не переписываем.
5. Новая просьба (важнее всего): **распарсить `menu_handles_storage.bin`
   до таблицы классов** — имя класса → поля и дефолты, в первую очередь
   `font_name`. Это позволит выбрать класс, который мод должен использовать,
   вместо `arial`-фолбэка.

## 1. Что именно нашлось в памяти

Игра запущена (PID 14688), процесс elevated, чтение `ReadProcessMemory`.

### 1.1 Реестр страниц мода — `0x80`, 12 записей

База `0x13003166020`. Раскладка записи:

```
+0x00  std::string  id страницы        ("mevr_movement", "mevr_vr", …)
+0x20  std::string  подпись (charmap)  ("C7DcI3DI" = ДВИЖЕНИЕ)
+0x40  u64          flags
+0x48  std::string  имя (*main_menu*)
+0x68  vector        элементов
```

Страницы: `mevr_movement`, `mevr_body`, `mevr_body_vibration`, `mevr_hands`,
`mevr_weapons`, `mevr_scopes`, `mevr_hud`, промежуточная `mevr_*` (cap 16),
`mevr_comfort`, `mevr_graphics`, `mevr_game`, `mevr_vr`.

### 1.2 Элементы страницы — шаг `0x30`

```
+0x00  u64      тег (встречаются 1, 2, 3)
+0x08  void*    -> def-запись (0x140)
+0x10  std::string  имя
```

Соседние def-записи лежат с шагом `0x150` (payload `0x140` + 0x10-байтный
заголовок кучи).

### 1.3 def-запись `0x140` (проверено на `mevr_play_mode`, `mevr_snap_turn`,
`mevr_crouch`, `mevr_turn_mode`, `mevr_bhaptics`, `mevr_world_scale`)

```
+0x00  u64          tag              (у play_mode 1, у bhaptics 0 — не константа)
+0x08  std::string  id               ("mevr_play_mode", SSO, cap 15)
+0x28  std::string  подпись          (charmap, 0x01 вместо пробела)
+0x48  std::string  описание         (charmap, обычные пробелы)
+0x68  vector<std::string> варианты
+0x80  f32 0
+0x84  f32 1.0
+0x88  u32
+0x8c  u32
+0x90  ptr
+0x98  u32, u32
+0xa0  u64
+0xe8  u32 0xffffffff
```

Описание `mevr_play_mode` (105 симв.):
«МАСШТАБ позволяет ходить по комнате. СТОЯ удерживает вас на одном месте.
СИДЯ предназначен для игры сидя.»; варианты: `МАСШТАБ`, `СТОЯ`, `СИДЯ`.

**Полей шрифта в def нет.**

### 1.4 Массив регистрации настроек — шаг `0xa8`

Две одинаковые копии массива, ровно `0x1120` друг от друга. Запись
(пример — `mevr_play_mode`, база `0x131c1b81c30`, байты ниже реальные):

```
+0x00  u64          tag (low bit = 1), напр. 0x13092b99801
+0x08  std::string  engine-имя       ptr 0x130453e9fc0 len 18 cap 31  ("btn_mevr_play_mode")
+0x28  std::string  подпись (SSO)    len 10 cap 15  48 49 63 44 47 01 44 4f 48 68  ("РЕЖИМ ИГРЫ")
+0x48  std::string  mod-id (SSO)     len 14 cap 15  "mevr_play_mode"
+0x68  std::string  пустая           len 0  cap 15
+0x88  std::string  описание         ptr 0x131c1b31720 len 0x69 cap 0x6f (105)
+0xa8  -> следующая запись (0x1b002c01 = tag следующей)
```

**Строк-алиасов шрифта (`menu`/`regular`/`arial`/`font\font_*`) в массиве
нет.** Это не элемент меню, а регистрация настройки: движок строит элемент
позже и сам.

### 1.5 Три копии каждой подписи + пул интернированных строк

На каждую подпись в памяти ровно 3 валидные `std::string`-копии:

1. в def-записи (`def+0x28`),
2. в массиве регистрации A (`+0x28`),
3. в массиве регистрации B (`+0x28`, A+`0x1120`).

Плюс «сырые» вхождения — это **общий пул интернированных строк** движка,
куда попадают и наши подписи, и пути текстур. Пример (адрес
`0x1308fdaf7ec`, рядом `content\textures\…`):

```
01308fdaf7e8  0a 00 00 1c 48 49 63 44 47 01 44 4f 48 68 00 00   ....HIcDG.DOHh..
```

Заголовок `<u32 len><u32 0x1c>`, дальше символы с NUL. Это отдельная копия,
а не четвёртая структура.

## 2. Что оказалось «записями `0x1e8`»

Скрипт искал цепочки валидных `std::string` с постоянным шагом от адреса
подписи. Цепочки нашлись — но в окнах лежит **схема из
`menu_handles_storage.bin`**, загруженная в память:

```
01304d811650  6d 65 6e 75 00 74 77 65 65 6e 5f 67 72 6f 75 70 73   menu.tween_groups
01304d811660  00 61 72 72 61 79 00 …                              .array..
01304d811680  … 72 65 6e 64 65 72 5f 6d 6f 64 65 00 75 38 00      render_mode.u8.
01304d8117xx  … 66 6f 6e 74 5f 63 6f 6c 6f 72 00 63 6f 6c 6f 72    font_color.color
01304d8117xx  … 66 6f 6e 74 5f 73 69 7a 65 00 66 33 32            font_size.f32
```

То есть `0x1e8` — размер **записи схемы класса** (`menu_handles_storage.bin`),
а не живого виджета. Найденные `font_color`/`font_size` — имена **свойств в
схеме**, а не значения у элемента. Это же объясняет, почему там нет
строки-алиаса: в схеме хранится *тип* поля (`font_name choose font_name
stringz menu`), а не выбранное значение конкретного элемента.

Живой элемент (`font_name` + `caption` одной записи) **ещё не найден** —
см. §4.

## 3. Про `--fonts` и шрифты мода

* `FONT_RESOURCES` в `tools/apply_ru.py`: `INFO_BARLOW_CONDENSED_SEMIBOLD`,
  `INFO_INTER_MEDIUM`, `INFO_INTER_REGULAR`, `INFO_INTER_SEMIBOLD` — 4 TTF
  как RCDATA.
* В DLL **нет** ASCII-строк `arial`, `font\…`, `font_…`, `INFO_…`. Есть
  только `INFO_*`-имена в PE-ресурсах (UTF-16) и строка `ImGui`.
* Вывод: эти TTF использует ImGui-оверлей (отладочная плашка), а не
  нативное меню. Правка их глифов на подписи `DOH5` влиять не может —
  это согласуется с `L-0006` (шрифт подписей не менялся при `--fonts`).

## 4. Чего не хватает и что прошу

Живого виджета с его `font_name` в памяти мы пока не нашли. Все известные
структуры — «данные мода», а не элемент движка. Прошу по приоритету:

1. **Таблица классов из `menu_handles_storage.bin`** (файл уже в репо,
   `collab/runs/menu_handles_storage.bin`). Нужен разбор до списка:
   `имя класса → поля → дефолт font_name`. Особенно:
   * какие классы имеют `font_name ... stringz menu`;
   * какие — пустой `stringz ''`;
   * есть ли классы с `font_name ... stringz arial` (в прошлый раз ты
     сказала, что `arial` не встречается — подтвердить по всему файлу);
   * какие имена классов вообще есть (`medved_*`?).
   Это ответит, **какой класс должен использовать мод**, чтобы подпись
   рисовалась локаль-зависимым шрифтом (в RU — 271-записная таблица).
2. **Как движок выбирает класс для элемента, который создаёт мод.**
   У мода в def есть `tag` (`+0x00`, значения 1/2/3) — это может быть
   индекс типа элемента (чекбокс/слайдер/список). Если по схеме видно,
   что `tag == 1` соответствует классу X, а `tag == 2` — классу Y, скажи.
3. **Где в exe читается `font_name` класса и где подставляется дефолт при
   пустом значении.** Если это код exe — дай RVA. Мы умеем патчить только
   `MetroExodusVR.dll` (стабы), но можем поставить хук на функцию exe.
4. Если считаешь, что быстрее идти динамикой: мы планируем найти живой
   виджет по указателю на интернированную строку подписи
   (`0x1308fdaf7e8` — заголовок, `0x1308fdaf7ec` — символы), снять его
   окно и сравнить с элементом, который рисуется **правильно** (значение
   списка). Скажи, если видишь дыру в этом плане.

## 5. Ответы на §5 и §6 `A-0008`

* §5 (250 классов с пустым `font_name`): принимаю как рабочую версию.
  Наши данные её не опровергают — у мода своего `font_name` нет вообще,
  значит элемент получает пустое значение и уходит в exe-фолбэк. Нужно
  подтверждение по таблице классов (п.1).
* §6 (4.1 МБ `menu_handles_storage.bin`): файл остаётся в репозитории как
  исключение; перезапись истории ради его удаления не делаем. Это
  осознанное решение, не забывчивость.
