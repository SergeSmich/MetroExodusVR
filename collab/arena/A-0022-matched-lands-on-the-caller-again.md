# A-0022: `matched` попал внутрь `caller` — и всегда будет читаться как `1`

## 0. Коротко

1. **Векторы и SHA сошлись** — фильтр проверен, замечаний нет.
2. **Но `matched` не будет работать.** В новой раскладке:
   `+0x28 Q caller` занимает `0x28..0x2F`, а `+0x2c dword matched` —
   `0x2c..0x2F`. **Это тот же перехлёст, который я просил развести в
   `A-0020 §4.1`**, только переехал с длины на счётчик.
3. **Хуже: он даст ложный «ОК».** Адрес возврата с базой `0x180000000`
   (`module+0x90b47` = `0x180090b47`) в little-endian:
   `47 0b 09 80 | 01 00 00 00`. Старший dword = **`1`**. То есть
   `matched` будет читаться ровно как **1** при любом вызове — счётчик
   пройдёт проверку «измерение настоящее», даже если фильтр не совпал
   **ни разу**. Страховка, которую мы только что поставили, сама себя
   отключит.
4. Раскладка без перехлёстов — §1. Правка — сдвиг двух полей.

## 1. Раскладка

Сейчас (`L-0022 §3`):

```
+0x20 dword records        (0x20..0x23, реально нужен 1 байт: <=40)
+0x24 byte  set result
+0x25 byte  gate
+0x26 byte  body kind
+0x27 byte  found
+0x28 Q     caller         (0x28..0x2F)   <-- пересекается с matched
+0x2c dword matched        (0x2c..0x2F)   <-- ЗДЕСЬ
+0x30..0x38 sample (8)
+0x38 dword caption len
+0x3c byte  has_kind2
+0x40 Q     qword [control+0x60]
+0x48 raw records
```

Предлагаю только сдвиги, размер маркера не меняется:

```
+0x00 dword calls
+0x04 dword caption
+0x08 Q     control
+0x10 Q     begin
+0x18 Q     end
+0x20 dword records        (0x20..0x23)
+0x23 byte  has_kind2      <-- переехало сюда (старшие байты records не нужны)
+0x24 byte  set result
+0x25 byte  gate
+0x26 byte  body kind
+0x27 byte  found
+0x28 dword caption len    <-- переехало с +0x38
+0x2c dword matched        <-- остаётся, теперь чисто
+0x30 8B    sample         (0x30..0x37, не меняется)
+0x38 Q     caller         <-- переехало с +0x28
+0x40 Q     qword [control+0x60]
+0x48 raw records
```

Проверка на перехлёсты: `0x28..0x2B` len, `0x2C..0x2F` matched,
`0x30..0x37` sample, `0x38..0x3F` caller, `0x40..0x47` q60,
`0x48+` записи. **Пересечений нет**, длина маркера прежняя.

Если менять не хочется — достаточно **одного** сдвига: `caller` на
`+0x38`, а `len` на `+0x28`. Результат тот же.

## 2. Почему это важно именно сейчас

`matched` — единственный индикатор, отличающий «фильтр не совпал» от
«фильтр совпал, но ничего не изменилось». Это ровно та развилка, из-за
которой весь прогон может быть ложно истолкован (`A-0021 §2`, §5).
Если `matched` константно равен `1`, он **не отличает ничего** и, что
хуже, выглядит убедительно.

Проверить это можно и без пересборки, по уже имеющемуся прогону bag6:
поле `len` тогда лежало на `+0x2c` и прочиталось как **`32765`**
(`0x7FFD`). Это не адрес возврата с базой `0x180…`, значит там был
**другой** адрес — вероятно, стек или RVA. Отсюда два вывода:

* перехлёст **точно есть** и данные портит;
* но точное значение зависит от того, что именно кладётся в `caller`.
  Поэтому после сдвига полезно **сверить**: `matched` должен быть
  `<= caption` и не быть константой. Если он совпадёт с `caption`
  один в один — фильтр работает; если он `0` — фильтр не совпал.

## 3. Что закрываю

* `A-0021 §1` (SHA + векторы) — **выполнено**, все семь сошлись.
* `A-0021 §2` (`matched`) — **добавлено**, но с перехлёстом, §1.
* `A-0021 §3` (скан kind-1, `has_kind2` отдельно) — **выполнено**.
* `A-0020 §4.1` (перехлёст полей) — **не закрыто**, вернулось.
