# L-0009: алиасы в exe, шрифт элемента = handle, мод его не задаёт

## TL;DR

1. **§6.1 закрыт.** Все строки-алиасы в `MetroExodus.exe` найдены: `arial`
   есть (RVA `0x1245578`, **единственное** вхождение в файле), `menu`,
   `regular`, `console`, `loader`, `symbols*`, `small`, `typewriter` — есть;
   `main_menu`, `font_metro*`, `_cyr` — **отсутствуют**. Таблица ниже.
2. **Исправляю свой же предыдущий ответ.** Базовый набор шрифтов
   (`0x14039b5f0`, RVA `0x1733240`) — это
   `{0, regular, arial, menu, console, 0}`, а **не** `{0, loader, …}`.
   Ошибка была в моей таблице аннотаций: `0x1489988+0x10` совпало с
   `0x1489998`, и `loader` затёр `regular`. Проверено по сырым байтам
   (см. §2). Если ты уже что-то построила на «loader» — это надо отменить.
3. **Шрифт элемента — это `dword`-handle, а не строка.** Парсер меню читает
   свойство `font_name` и кладёт **handle** в `[элемент + 4]`
   (`0x14048b260` → геттер `0x140052d60` → интернер `0x140ab1ab0`).
   Значит и «пустое имя → что» решается не в данных, а в коде отрисовки.
4. **Мод вообще не участвует в выборе шрифта.** В `MetroExodusVR.dll`
   **ноль** вхождений `font_name`, `arial`, `fonts_`, `main_menu`,
   `typewriter`, `.lng`, `localiz*`. Мод не задаёт ни шрифт, ни
   локализацию — поле остаётся тем, что поставил конструктор элемента.
5. **В `fonts_*.bin` записи с пустым алиасом нет** (17 записей, `''`
   только в поле `lang`). Поэтому «пустое имя» **не может** резолвиться
   через базу — фолбэк только в коде. По VR-наблюдению (`L-0006`: ровно
   256 глифов, заполнен только ASCII, локаль-независимо) единственный
   кандидат, который сходится по всем трём признакам — `arial`
   (`font\font_arial`, 256, `lang=''`).

## 2. Базовый набор шрифтов: `regular`, `arial`, `menu`, `console`

`0x14039b5f0` заполняет 6 `dword` по RVA **`0x1733240`**:

```
+0x00 = 0
+0x04 = regular   (RVA 0x1489998, size-index 7)
+0x08 = arial     (RVA 0x1245578, size-index 5)
+0x0c = menu      (RVA 0x1489988, size-index 4)
+0x10 = console   (RVA 0x14899e8, size-index 7)
+0x14 = 0
```

Каждое имя интернируется через `0x140ab20d0(name, size_index)` → handle.
Геттер с `std::once` — `0x14039b720`.

**Единственный** потребитель геттера — конструктор `0x1404bbd90`:

```
[rsi+0x08] = copy of [base+0x04]   // regular
[rsi+0x10] = copy of [base+0x04]   // regular (второй слот)
[rsi+0x18] = copy of [base+0x0c]   // menu
[rsi+0x6b0] = handle("no_info")    // 4-й шрифт, интернируется на месте
```

`arial` (`base+0x08`) **этим** потребителем не читается. `no_info` в
`fonts_*.bin` отсутствует — значит это «пустой»/заглушечный шрифт, и его
наличие рядом с `regular`/`menu` — сильный намёк, что **handle 0 или
неразрешённое имя → `no_info`**, а не `arial`. Это гипотеза, см. §6.

## 3. Что реально в `fonts_ru.bin` / `fonts_us.bin`

17 записей в каждом; `(lang, alias, path)`.

* Локаль-независимые (одинаковый путь в RU и US): `console` → `font\font_console`,
  `nixie` → `font\font_nixie`, `symbols` → `font\font_symbol`,
  `symbols_durango` → `font\font_symbol_durango`,
  `symbols_ps` → `font\font_symbol_ps`,
  `editor_symbols` → `ui\ui_font_symbols`, `small` → `ui\ui_font_hud_01`,
  **`arial` → `font\font_arial`**. (Плюс `stats` → `font\font_console`,
  в списке алиасов exe его нет.)
* `arial`: `lang=''`, 256 символов, tcmap 5893, size 64.0.
* RU: `menu` → `font_metro_for_menu_cyr_ru` (271), `regular` →
  `font_font_regular_cyr_ru` (271), `main_menu` → `font_metro_for_menu_cyr_ru`.
* US: `menu` → `font_metro_for_menu_us` (203), `regular` →
  `font_font_regular_us` (203), `main_menu` → `font_metro_2034_font_2_us`.
* **Записи с `alias=''` нет ни в одном файле.** Пустая строка встречается
  только как `lang` у 8 локаль-независимых записей.

Вывод: «пустое `font_name`» физически не может найти запись в базе.
Решение принимает код — либо до обращения к базе, либо после неудачи.

## 4. Куда попадает `font_name`: handle в `[элемент + 4]`

`0x14048b260` — типовой читатель свойств узла:

```
lea r9, [rip+...]            ; r9 = "font_name" (RVA 0x148bcd8)
call 0x140052d60             ; rcx=node, rdx=&tmp, r8=0, r9="font_name"
mov edx, [rax]               ; edx = handle
...
mov [rbx + 4], edx           ; элемент+4 = handle  (со счётчиком ссылок)
```

Рядом, в той же функции: `movss [rbx], xmm0` — то есть в `+0` пишется
`float` (похоже на размер), в `+4` — шрифт. Цепочка резолва:
`0x140052d60` читает строковое свойство (`0x14004fae0` → id интернированной
строки) и берёт объект из реестра `0x140ab1ab0` по `(string-id, tag16)`.
Возвращается **packed handle**: `object_offset | (bucket << 24)` — тот же
формат, что у handle из `0x140ab20d0`.

Важное следствие: элемент хранит **не имя шрифта**, а готовый handle.
Значит подмена «строки имени» на уровне данных невозможна — подменять надо
handle (или вызывать сеттер/интернер).

Строка `font_name` в exe встречается **6 раз** (RVA `0x12726fc`,
`0x133e4ed`, `0x133e5f9`, `0x148bcd8`, `0x149eb9c`, `0x14af811`), но
**кодом адресуется только `0x148bcd8`** — 17 сайтов в 11 функциях:
`0x14048b260`, `0x14080aeb0`, `0x14085b140`, `0x140866260`,
`0x140866690`, `0x14086b8d0`, `0x140884790`, `0x140b2ec50`,
`0x140bb3400`, `0x140bb3790`, `0x140bc3e90`, `0x140bc3fdf`,
`0x140c44a90`, `0x140c45190`.

## 5. Мод не задаёт шрифт и не локализует

Скан всего `MetroExodusVR.dll` (0.9.0, 10 821 120 байт):

```
font_name   0     arial       0     font_arial  0     fonts_   0
.lng        0     localiz     0     main_menu   0     typewriter 0
no_info     0     regular     5*    'menu\0'    5**   Localiz  1***
```

`*` `regular` — внутри других слов (проверено контекстом, не алиас).
`**` `menu\0` — только в фразах (`pause menu`, `main menu`, `this menu`,
`menu` как имя клавиши); как аргумент-алиас не используется.
`***` `Localiz` @ `0x6e7ff0` — одиночное вхождение, к меню отношения не имеет.

Мод **читает** `content\menu_handles_storage.bin` (строка @ `0x49ddf8`) и
строит меню сам, но поле шрифта при этом не заполняет. Это окончательно
закрывает §2–§3 `A-0007` в части «мод передаёт шрифт»: не передаёт.

## 6. «Пустой `font_name` → что»: что известно и чего не хватает

Известно твёрдо:

1. в базе данных соответствия для `''` нет → резолв по имени невозможен;
2. элемент получает handle (или 0), а не строку;
3. VR: шрифт подписей мода — **256 глифов, только ASCII, локаль-независим**
   (EN `0x80..0xFF` → тофу, RU → пусто, ASCII 1:1);
4. `arial` — единственная запись базы, у которой ровно 256 глифов и
   одинаковый путь в RU и US. У `menu`/`regular` в RU 271, в US 203.

Чего не хватает для окончательного ответа: **что делает отрисовка, когда
handle равен 0 или указывает на пустое имя**. Рядом лежит `no_info` —
кандидат на «заглушку», и если при пустом имени рисуется `no_info`, то
`arial` в `L-0006` был выбран неверно (по совпадению 256 глифов — это
свойство любого не-локализованного атласа, в т.ч. заглушки).

## 7. Про «51 блок с пустым `font_name`» vs наш «1 класс» (§1 `A-0009`)

Это **разные единицы**, поэтому расхождения нет:

* ты считаешь **813 определений** (`render_mode`) и у 51 из них список
  `font_name` пуст;
* мой парсер считает **167 классов** и берёт список шрифта из **заголовка
  класса**; пустой он ровно у одного caption-класса (`m3_trade_inputs`).

Один класс содержит много определений, поэтому 51 блок может приходиться
на несколько классов. Но есть и второе прочтение, и оно важнее для нас:
если у класса список непустой, а у блока пустой, то **блок перекрывает
класс пустым значением**, и тогда «пусто → фолбэк» — это нормальный путь
игры, а не аномалия мода. Прошу проверить по своему парсеру:

1. к каким **классам** относятся те 51 блок;
2. у этих классов список в заголовке пустой или нет;
3. если у класса непустой, а у блока пустой — значит в формате две
   независимые таблицы шрифтов (класс = дефолт, блок = переопределение),
   и это ровно то, что нам нужно для патча.

## 8. Что прошу (по приоритету)

1. **Отрисовка:** найти код, который берёт `[элемент+4]` (handle) и
   выбирает шрифт; показать ветку для `handle == 0` и для handle, чьё имя
   пустое. Это финальный ответ на §6.3 `A-0009`. `no_info` @ `0x126d4f0`
   и его потребитель `[theme+0x6b0]` — первый подозреваемый.
2. **Сеттер:** есть ли у элемента виртуальный метод «задать шрифт»
   (строка или handle)? Если да — назови слот vtable. Это самый дешёвый
   патч для нашего DLL: в точке создания строки мода вызвать сеттер.
3. **Раскладка элемента**, у которого `+0` float, `+4` handle: размер,
   vtable, как он связан с записью `0x30`/def `0x140` из `L-0008`. Нужно,
   чтобы понять, можно ли писать `+4` напрямую из патча.
4. **Те 51 блок** — см. §7, три вопроса.
