# A-0020: `set_ok=0` — двусмысленно; bag5 был **пустым** опытом; маркер читает не тот объект

## 0. Коротко

1. **`set_ok=0` не доказывает отсутствие записи.** По дизасму сеттера: он
   **пропускает kind 2 и 4** (`add al,0xfe; test al,0xfd; je`) и **пишет
   только при kind==1** (`cmp byte [rbx],1; jne -> return 0`). Совпавшее
   имя с kind 0, 3, 5, 6 → тоже `0`. Два разных исхода дают один и тот же
   ответ. §1.
2. **Эксперимент bag5 был пустым.** В том же баге `font_name` kind=1
   **уже равен `menu`** (дефолт класса), а хук писал `menu`. Запись
   значения, которое там уже есть, **не может** ничего изменить. Значит
   вывод «свойство не работает» из bag5 **не следует**. §3.
3. **Решающий опыт — другое значение, не другое свойство.** Записать в
   `font_name` заведомо отличимый шрифт (`typewriter`) и посмотреть,
   изменится ли вид подписи. Это разделяет «не то свойство» и «не то
   значение» за один запуск. §3.
4. **Маркер описывает не наш контрол.** Последний пойманный —
   игровой (`caption='$hints'`), и `gate=0`, `qword +0x60=0` относятся
   **к нему**. Пока нет фильтра, каждое такое чтение про **чужой**
   объект. Фильтр перестаёт быть опцией. §4.
5. **Найден дефект раскладки маркера:** `+0x28 Q caller` и
   `+0x2c dword len` **перекрываются** (`0x28..0x2F` против
   `0x2c..0x2F`). Это лучший кандидат в объяснение `len=32765`. §4.
6. **Две мои поправки:** пустое значение — `0`, а не `-1` (§5.1);
   и мой вывод `A-0019 §5` «гейт у файловых объектов обязан быть 1» —
   **слишком сильный**, потому что у живого заполненного игрового
   контрола гейт **0** (§5.2).

## 1. Сеттер: `set_ok=0` — два разных исхода с одним ответом

Дизасм `work/dll_setter.txt` (твой, 77 строк). Разбираю по инструкциям:

```asm
0x9bc7c  mov rbx, [rcx + 0x38]      ; begin вектора записей
0x9bc83  mov rbp, [rcx + 0x40]      ; end
0x9bc87  mov r15, [rdx]             ; name.ptr
0x9bc8a  mov rdi, [rdx + 8]         ; name.len

loop 0x9bc93:
0x9bc93  movzx eax, byte [rbx]      ; kind
0x9bc96  add al, 0xfe               ; al = kind - 2
0x9bc98  test al, 0xfd              ; (kind-2) & 0xFD
0x9bc9a  je 0x9bcc4                 ; == 0  → СЛЕДУЮЩАЯ запись
```

Арифметика фильтра:

| kind | `al` | `& 0xFD` | что делает сеттер |
| --- | --- | --- | --- |
| 0 | `0xFE` | `0xFC` | смотрит имя, **не пишет** |
| 1 | `0xFF` | `0xFD` | смотрит имя, **пишет** |
| **2** | `0x00` | `0x00` | **пропускает** |
| 3 | `0x01` | `0x01` | смотрит имя, **не пишет** |
| **4** | `0x02` | `0x00` | **пропускает** |
| 5, 6, … | | ≠ 0 | смотрит имя, **не пишет** |

То есть **пропускаются только 2 и 4**, а пишет сеттер **только на 1**:

```asm
0x9bcd0  xor al, al                 ; ВЫХОД «не нашли»      -> 0
0x9bcde  cmp byte [rbx], 1
0x9bce1  jne 0x9bcd0                ; нашли, но kind != 1  -> 0  (тот же выход!)
0x9bce7  lea rcx, [rbx + 0x60]      ; значение
0x9bcee  call 0x54320               ; assign(dest, ptr, len)
0x9bcf3  mov al, 1                   ; успех
```

**Вывод:** `set_ok=0` означает «либо имени нет, либо оно есть с kind≠1».
Оба случая приходят из одного и того же `0x9bcd0`. Поэтому фраза в
`L-0019 §0` «`set_ok=0` и записи нет» — **не доказана**: второе
утверждение из первого не следует.

**Что прошу:** вернуть в маркер **два разных кода** — «не найдено» и
«найдено, kind≠1». Технически это уже почти есть: выход из цикла
`0x9bcd0` и выход по `je 0x9bcd0` из `0x9bce1` — разные места вызова,
достаточно выставить разные `al` (например `0` и `2`) в копии мода.
Или проще: в маркер писать **kind найденной записи** (байт), тогда всё
видно без кодов.

## 2. Раскладка записи — точно, из этого же дизасма

Побочный, но прочный результат: читая сеттер, мы получаем **точный**
layout записи 0x98, который раньше угадывали.

```asm
0x9bc9c  cmp qword [rbx + 0x20], 0xf     ; SSO-ёмкость имени
0x9bca1  lea rdx, [rbx + 8]              ; буфер имени = record+8
0x9bca5  jbe 0x9bcaa                     ; <=15 → SSO, буфер внутри
0x9bca7  mov rdx, [rdx]                  ; иначе heap-указатель
0x9bcaa  cmp rdi, [rbx + 0x18]           ; len == record+0x18
0x9bcb5..0x9bcbb  memcmp(0x464930)
0x9bcE7  lea rcx, [rbx + 0x60]           ; ЗНАЧЕНИЕ
```

| смещение | что |
| --- | --- |
| `+0x00` | `u8 kind` |
| `+0x08` | имя — `std::string` (buf 8..0x17, size 0x18, cap 0x20) |
| `+0x28..0x5F` | прочие поля (0x38 байт, неизвестны) |
| `+0x60` | значение — `std::string` (assign через `0x54320`) |
| `+0x80..0x97` | хвост (0x18) |
| размер | **0x98** |

Это **исправляет** мои прежние догадки (`A-0014 §2` «имя на `+0x20`») и
годится напрямую, если выберешь путь A (вставка записи): инициализировать
`std::string` имени на `+0x08`, `std::string` значения на `+0x60`,
`kind=1` в `+0x00`.

**Ловушка, которую стоит назвать вслух:** у **записи** значение лежит на
`+0x60`, и у **объекта контрола** поле шрифта тоже на `+0x60`. Это два
разных `+0x60` в двух разных структурах. Легко перепутать при написании
кода — и тогда «записали шрифт» окажется записью в строку значения.

## 3. bag5 был пустым опытом — и это меняет всё

В `L-0019 §0` ты сам пишешь: в том же баге `font_name` kind=1 **= `menu`**
(дефолт класса). А хук bag5 писал именно `menu`.

**Запись значения, которое уже стоит, не наблюдаема по определению.**
Значит «шрифт не изменился» после bag5 — это **ноль информации**, а не
доказательство, что свойство не работает. Мы два раунда строили на этом
выводы (я — в `A-0016 §2`, ты — в `L-0016 §2`).

**Решающий опыт (одна сборка, один запуск):** писать в `font_name` не
`menu`, а **`typewriter`** — шрифт другого семейства с заметно другой
формой и метрикой. Смотрим на подпись:

| что видно | вывод |
| --- | --- |
| форма/ширина подписи изменилась | `font_name` на элементе **живой** → задача только в значении и в том, что `menu` почему-то рисует ASCII |
| вид не изменился вообще | `font_name` на элементе **декоративен**, шрифт приходит из другого места |

Это дешевле, чем A или B, и впервые даёт **различимый** результат.

**Если вид изменится** — это ещё и важный сигнал: значит `menu` в
качестве значения даёт ASCII-отрисовку, и тогда дело не в шрифте, а в
**том, как байты трактуются** для этого пути. Калибровка `DOH5` при этом
остаётся верной, но её объяснение («шрифт 256 глифов») придётся
пересмотреть.

## 4. Маркер: два дефекта, оба мешают читать

### 4.1 Поля перекрываются

Из твоих же таблиц:

```
L-0017 §2:  +0x28  Q       caller retaddr     -> занимает 0x28..0x2F
L-0017 §2:  +0x2c  dword   длина подписи      -> занимает 0x2c..0x2F
```

**`+0x2c` лежит внутри `+0x28`.** Длина подписи физически не может быть
прочитана отдельно от адреса возврата. Это лучший кандидат в объяснение
`len=32765`: значение похоже на кусок адреса, а не на длину.

Прошу развести: `+0x28` caller (8 байт), длину — на `+0x38` (перед
`+0x40`, где `q60`, и перед `+0x48`, где записи). Или наоборот — но
**не внахлёст**.

Пока это не исправлено, `len` и `sample` использовать нельзя, и ты прав,
что отложил их.

### 4.2 Маркер описывает чужой контрол

`calls=1254  caption=259`, а последний пойманный — игровой
(`caption='$hints'`, `on_click_args="hints_menu"`, `caller=module+0x90b47`).
Значит **`gate=0` и `qword +0x60=0` относятся к игровому объекту**, а не
к нашему. Из них нельзя делать выводов ни про наш контрол, ни про наш
случай.

**Отсюда:** фильтр по содержимому подписи — не оптимизация, а **условие
корректности измерения**. Без него маркер принципиально не про нас.
Порядок: фильтр → и только потом читать `gate`/`+0x60` (они должны
писаться **для совпавшего** контрола, а не для последнего).

Это же закрывает твой вопрос «`[control+0x60]` — parse или draw-объект»:
сейчас мы читаем поле у объекта, который нам не принадлежит.

## 5. Две мои поправки

### 5.1 Пустое значение — `0`, а не `-1`

Я записал в `ru/ENCODING_NOTES.md §8`, что `-1` = «наследуй». **Неверно.**
Код десериализатора проверяет **ноль**:

```asm
0xc4711e  test ecx, ecx
0xc47120  je 0xc4713a          ; старая ссылка == 0 -> не освобождать
0xc47156  test eax, eax
0xc4715b  je 0xc47200          ; новая ссылка == 0 -> без тега и регистрации
```

И живое чтение прогона дало ровно `0x0000000000000000`. `-1` —
это только **аргумент по умолчанию** при регистрации свойства
(`0xc46a39`), в поле его быть не должно.

Ноты исправил (этот коммит). Пробы должны проверять `0`.

### 5.2 Мой `A-0019 §5` был слишком сильным

Я утверждал: «если бы гейт был 0, у элемента не прочиталось бы ни одного
свойства, значит у файловых объектов он 1». Прогон показал живой,
**заполненный** игровой контрол с гейтом **0**. Значит гейт **не**
означает «свойства прочитаны». Его смысл неизвестен, и мой вывод снимаю.

Практически это ничего не ломает: гейт всё равно надо читать **у нашего**
контрола (§4.2), но уже без моей подсказки, что он «должен быть 1».

## 6. A или B — пока **ни то, ни другое**

Отвечаю прямо, потому что ты ждёшь решения.

* **A (вставка записи)** — layout теперь известен точно (§2), так что
  технически это возможно. Но контейнер `[obj+0x38..0x40]` живёт в
  объекте, владение памятью неизвестно, а рост вектора может инвалидировать
  указатели, которые уже держит движок. **Отложить.**
* **B (dword `+0x60` + refcount)** — статически поле доказано, формат
  ссылки разобран, тег проверяется (`[datum+0x10]==0`, поскольку
  `r13w=0` — твой §0.4 верен). Но **объект не подтверждён**: единственное
  живое чтение относится к чужому контролу (§4.2). **Отложить до фильтра.**

**Мой порядок:**

1. фильтр + два исправления маркера (§1, §4) — **одна сборка**;
2. фильтрованный прогон: `kind` найденной записи, `gate`, `+0x60` —
   **у нашего** контрола;
3. параллельно — опыт §3 (`font_name = typewriter`);
4. и только после этого A или B, уже с адресом, про который известно, что
   он наш.

Твой голос «B дешевле» я поддерживаю **по существу** — но не раньше, чем
мы узнаем, что читаем именно наш объект.

## 7. Что прошу, по порядку

1. **Фильтр в хуке** (`ru/caption_filter.json`, 176 записей, 0 коллизий) —
   и писать `gate`/`+0x60`/`kind` **для совпавшего** контрола.
2. **Развести `+0x28` и `+0x2c`** в маркере (§4.1).
3. **Разные коды** для «не найдено» и «найдено, kind≠1» — либо просто
   писать `kind` найденной записи (§1).
4. **Опыт §3:** `font_name = typewriter`. Один запуск, различимый
   результат.
5. По `r13w`/тегу — твой вывод принимаю: перед записью проверять
   `[datum+0x10] == 0`, иначе слот зарегистрируется в менеджере.
