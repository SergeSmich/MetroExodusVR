# L-0030: живая таблица `Fonts` **не пуста**; хвост записи `font_name` пуст; две поломки инструмента

## 0. Итог

1. **`menu` резолвится.** `[exe+0x1733240]` (объект `Fonts`, на него же
   указывает self-ptr по `exe+0x1733260`) в живом процессе содержит
   **все четыре** ненулевых handle:
   `regular=0x17056dc0`, `arial=0x17056eb8`, **`menu=0x001c58a0`**,
   `console=0x05055fe8`. Независимый обход хеш-таблицы менеджера
   (`work/resolve_fonts.py`) открывает каждый handle по банке и читает
   имя ноды: `regular`, `arial`, `menu`, `console`. Т.е. **имя → handle
   работает**, и `menu` в таблице есть.
2. Нули `fonts[1..4]` в bag11c/bag12 — **баг замера**, не факт игры
   (см. §1.2). `fonts[3] menu = 0` из L-0029 §2 **отзываю**.
3. `[rec+0x80]` (tail записи `font_name`) — **нули в двух прогонах**.
   Значит разрешённый handle не кэшируется в записи; гипотеза A-0027 §3
   не подтвердилась (§3).
4. Первый matched-контрол с записью `font_name`: `[control]=3`,
   `[control+0x60]=0` — как и у элемента списка (§4).

## 1. Две поломки, из-за которых прошлые числа были неверными

### 1.1 Крэш bag12 — shadow space

`0xab20d0` пишет **свои аргументы в shadow space вызывающего**:
`[rsp+8]=rcx`, `[rsp+0x18]=rbx`, `[rsp+0x20]=r9w` (дизасм по адресам
`0xab20d0/0xab20d5/0xab20db`). bag12 держал указатель маркера в
`[rsp]`/`[rsp+8]` (`push rsi; push rsi`), поэтому **первый же вызов
резолвера затирал его**, со второго — `rsi` = мусор, `R11` = мусорный
`exe+0xab20d0`, чтение по `-1`. В `logs\crash.log` (PID 14160):
`MetroExodusVR.dll+0x00C27EB5`, `read from FFFFFFFFFFFFFFFF`,
`R11=CF10A56000AB2290`, `RAX=CF10A560000001C0`.

Исправлено: `sub rsp,0x30`; маркер лежит в `[rsp+0x20]`, выше всех
слотов, которые трогает резолвер. bag13/bag14 в игре не падают.

### 1.2 Копия `Fonts[]` шла с шагом **1 байт**, а не 4

Было: `mov [rcx+r9+0x1a34], r10d` — SIB `0x09` (scale = 1). Каждый
dword заезжал на соседний, поэтому дамп показывал мусор
(`regular=0x00cd6190`, `arial=0x00008000`, `menu=0`). Надо SIB `0x89`
(scale = 4). Исправлены **обе** копии: до сета (`+0x1a34`) и после
(`+0x1ba4`). bag13/14 — с фиксом, `apply_ru.py` коммит `0cfff6a`.

### 2.1 Уточнение по раскладке (A-0027 §4)

* `exe+0x1733240` — **сам объект** `Fonts` (не 16 dword'ов слотов: значимых
  восемь).
* `exe+0x1733260` — qword **внутри** объекта (`+0x20`), хранит указатель на
  себя же (`Fonts*`).
* Слоты: `+0x00` pad, `+0x04 regular`, `+0x08 arial`, `+0x0c menu`,
  `+0x10 console`, `+0x14` 0, `+0x18 0x800000cd` (bank `0x80`, ноды нет —
  похоже на sentinel/невалидный handle), `+0x1c` 0.

## 3. Запись `font_name` (0x98), снята копией в маркер

Одинаково в bag11c и bag14 (второй билд — контроль):

```
+0x00  u64 kind = 1
+0x08  std::string name : SSO 'font_name' @+0x08, len@+0x18 = 9, cap@+0x20 = 0xf
+0x28  std::string type : 'stringz'   @+0x28, len@+0x38 = 7, cap@+0x40 = 0xf
+0x48 .. +0x5f    нули
+0x60  std::string value: 'menu'      @+0x60, len@+0x70 = 4, cap@+0x78 = 0xf
+0x80 .. +0x97    нули  ← tail
```

**Вывод.** В `[rec+0x80]` handle'а нет. Косвенно: handle не кэшируется в
записи, значит отрисовка берёт его в другом месте (класс/объект/вызов на
кадр), а не из записанного нами `font_name`. Значение `menu` в записи
лежит и переживает сеттер (подтверждено ещё раз), но на вид не влияет.

## 4. Первый matched-контрол с `font_name`

`[control] = 3`, `[control+0x60] = 0`. Совпадает с элементом списка, но
сам факт важен: у текстовых контролов первое слово — **маленькое целое**
(тег типа), не vtable. Q60 пуст.

## 5. Что закрыто, что нет

| Вопрос | Статус |
|---|---|
| `menu` есть в таблице имён | **да** (нода `menu`, bank 0) |
| имя `menu` резолвится в ненулевой handle | **да** (`0x001c58a0`) |
| `Fonts` пуст | **нет**, это был баг замера (§1.2) |
| handle лежит в `[rec+0x80]` | **нет** (нули, два прогона) |
| `font_name` меняет отрисовку | нет (206 записей, вид не менялся) |

Остаётся один адресуемый вариант: шрифт берётся из **слота `Fonts+0x08`
(arial)** или из класса. Прямой бинарный тест — подменить один dword:
`[Fonts+0x08] = [Fonts+0x0c]` (arial → menu), обратимо, живёт до
перезапуска. Если подписи станут кириллицей — фикс тривиален (одна
запись в ctor/после него), если нет — шрифт закреплён за классом.

**Визуально проверить сейчас не могу**: HMD не подключён
(`xrGetSystem(HMD) -> XR_ERROR_FORM_FACTOR_UNAVAILABLE (-35)`,
«VR remains inactive»), игра при этом жива, маркер снят. Поэтому §7.5
(скриншот) не сделан и **§7.6 (FSR/DLSS/TAA) визуально не подтверждён** —
код этих настроек хук не трогает, но картинки без шлема нет.
