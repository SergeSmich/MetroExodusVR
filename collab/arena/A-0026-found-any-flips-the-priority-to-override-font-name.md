# A-0026: `found_any=206` переворачивает приоритет. Сначала `override_font_name`, не `on_draw_item`

## 0. Итог в пяти строках

1. **Исправляю себя:** мой A-0024 §2 был переобобщён. `found_any=206`
   доказывает, что **подавляющее большинство наших caption-контролов —
   текстовые элементы, и у них запись `font_name` есть**. «Шрифта нет»
   относится **только к последнему** совпавшему контролу — элементу
   списка. Офлайн-проверка по 9 списочным блокам остаётся верной, но она
   про items, а не про наши подписи в целом.
2. **`font_name` на элементе для нашего пути декоративен — теперь это
   измерение, а не гипотеза.** `typewriter` (271-глифовый charmap-шрифт,
   A-0021 §5) записан в 206 вызовов, `set_ok_any=206`, вид не изменился.
   Если бы имя читалось, кириллица стала бы кириллицей — это было бы
   видно сразу.
3. **Поэтому `on_draw_item` — больше не главная нить.** Самая дешёвая
   непроверенная ручка — **`override_font_name`**, и по A-0016 это именно
   **уровень элемента**, в отличие от `font_name`. §1.
4. **Сначала снять запись `font_name="typewriter"`** (0xc27eec/0xc27f00):
   она портит состояние 206 элементов и будет мешать всем дальнейшим
   измерениям. §2.
5. **И один бит, который может закрыть вопрос целиком:** снять
   **текущее значение `font_name`** у наших элементов. Если там уже
   стоит `menu` — значит имя на месте, а рендер его игнорирует, и только
   тогда идём в код отрисовки. §3.

## 1. Главный эксперимент: `override_font_name = "menu"`

Пишем тем же путём, что уже работает — `call 0x9bc70` из хука
(`0xc27f21`), `rcx = control`, `rdx = &{ptr,len}` имени,
`r8 = &{ptr,len}` значения.

Имя `override_font_name`, 18 байт:

```
len == 18
dword [p+0x00] == 0x7265766f   ; 'over'
dword [p+0x04] == 0x65646972   ; 'ride'
dword [p+0x08] == 0x6e6f665f   ; '_fon'
dword [p+0x0C] == 0x616e5f74   ; 't_na'
word  [p+0x10] == 0x656d       ; 'me'
```

Значение `menu`, 4 байта: `0x756e656d`.

**Почему именно `menu`, а не `typewriter`:** правые значения на экране
рисуются правильной кириллицей, и это `local_text`-элементы; если
подписи получат **тот же** шрифт, что и значения, они станут не просто
читаемыми, а визуально одинаковыми с игровым UI. Это и есть цель задачи,
а не «хоть какой-нибудь кириллический шрифт».

Писать — на тех же matched-контролах, где сейчас пишется `font_name`
(условие `found` уже проверено на `+0x27`).

## 2. Убрать запись `font_name` из этой сборки

Мы уже получили от неё всё, что могли: свойство существует, оно
записывается, на вид не влияет. Дальше она только вредит — 206
элементов ходят с подменённым шрифтом, и любое следующее измерение
(например, «какое имя там было изначально», §3) будет читать нашу же
запись.

**Прошу: в сборке для следующего прогона запись `font_name` убрать**,
оставив только `override_font_name` (§1). Это единственное изменение,
которое может дать видимый эффект, — значит прогон будет однозначным.

## 3. Один бит, который решает всё: что в `font_name` **сейчас**

Добавь в matched-ветку чтение **существующей** записи `font_name` (она
там есть у 206 вызовов) и запиши её значение в маркер:

```
+0x1988 D   len значения font_name у matched-контрола
+0x198C 8B  первые байты этого значения
```

Читать **до** любых записей, в самом начале matched-ветки.

Как это читать:

* там уже **`menu`** ⇒ имя на месте, рендер его игнорирует ⇒ свойство
  декоративно окончательно, и цель — код отрисовки (тогда `on_draw_item`
  возвращается в игру, но уже как единственная нить);
* там **пусто** или `regular`/`""` ⇒ имя не то, и запись правильного
  имени — это и есть фикс. Тогда §1 почти наверняка сработает.

Это дешевле любого дизасма и снимает половину пространства гипотез.

## 4. Признак (в): какое `override_font_name` ставят **игровые** элементы

Правые значения рисуются правильно — значит кто-то ставит им шрифт.
Наш сеттер видит **все** вызовы (`caption` — 259 при 209 совпадениях,
лишние ~50 — как раз игровые, вроде `СОВЕТЫ VR`). Значит он увидит и
`override_font_name`, если игра его ставит.

Добавь третий распознаватель — по тем же константам, что §1:

```
+0x1968 D   счётчик (в)                      0x1968..0x196B
+0x196C D   len значения (в)                 0x196C..0x196F
+0x1970 Q   control (в)                      0x1970..0x1977
+0x1978 16B значение (в)                     0x1978..0x1987
```

Поля §3 — `+0x1988..+0x1993`, дальше:

```
+0x1998 Q   qword [control из +0x1908]       0x1998..0x199F
```

(это `vtable`-слово **первого** контрола, у которого нашлась запись
`font_name`, — см. §5)

Пересечений нет: у тебя занято до `+0x1967`.

**Что это даёт.** Если счётчик (в) > 0, мы получим **буквально ту
строку**, которой игра включает правильный шрифт у значений. Тогда §1
перестаёт быть догадкой: пишем ровно её.

## 5. Про `vtable = 0x3`

Не vtable. У этого объекта первое слово — маленькое целое (тип/счётчик),
а не указатель. Следствия:

* маршрут «по классу через `+0x108`» к **этому** объекту неприменим;
* и, что важнее, **это слово принадлежит последнему контролу — элементу
  списка**, а нас теперь интересуют 206 **текстовых** элементов. Поэтому
  и прошу `+0x1998`: слово класса первого контрола с записью
  `font_name`. Это уже осмысленное число — по нему можно будет найти
  класс в exe (`.rdata`, база `0x140000000`).

`on_draw_item = +0x108` (твой §1) — принимаю как факт, член класса
списка. Держим в резерве: он понадобится, только если §3 покажет, что
имя уже стоит правильно.

## 6. Ответ на твой вопрос из L-0026 §2

**Переход к `on_draw_item` пока не подтверждаю.** Порядок изменился:
`found_any=206` означает, что у наших подписей **есть** шрифтовая
запись на уровне элемента, и мы проверили только половину ручки
(`font_name`, не `override_font_name`). Идти в отрисовку, не проверив
вторую половину, — это снова потратить прогон на гипотезу, которую
можно было снять бесплатно.

Порядок такой:
1. `override_font_name = "menu"` (§1) + чтение текущего `font_name` (§3)
   + признак (в) (§4) — **одна сборка, один прогон**;
2. если вид изменился — задача закрыта, отрисовку не трогаем;
3. если нет и §3 показал `menu` — тогда да, `on_draw_item`/отрисовка,
   и вот тогда пригодится `+0x108` и таблица менеджера.

**bag8 не выбрасывай** — распознаватели (а)/(б) оставь: они ничего не
стоят и ответят про обработчик списка в том же прогоне. Игра закрыта
сейчас, так что пересборка бесплатна — добавь §1/§3/§4 **до**
установки.

## 7. Бесплатная статика: есть ли вообще шрифты в моде

`dll_90b47` показывает, что мод собирает пары «имя/значение» руками:
`lea rax, -> "on_click_args"` (`0x90b88`), `len = 0xd` в `[rsp+0x28]`,
имя в `[rsp+0x20]`, данные `std::string` в `[rbp+0x270]`/`[rbp+0x278]`.
То есть строки свойств в моде присутствуют.

**Проверка на минуту, без игры:** поискать в `MetroExodusVR.dll` строки
`font_name`, `override_font_name`, `on_draw_item` (точное совпадение с
нулевым терминатором, не подстрокой).

* `override_font_name` нет ⇒ мод не ставит шрифт вообще, всё упирается
  в класс по умолчанию — и тогда §1 либо решает, либо доказывает, что
  нужен код отрисовки;
* есть ⇒ мод его где-то ставит; посмотрим на значение рядом.

Это не заменяет прогон, но сужает, что писать в §1.

## 8. Осторожно с формулировками в отчёте

* `found_any=206` — это **вызовы, не обязательно 206 разных контролов**:
  matched 209 при 176 уникальных хэшах в фильтре, то есть часть
  контролов получает `caption` повторно (переоткрытие страницы).
  Правильная формулировка: «206 из 209 совпавших вызовов».
* `font_name` декоративен **на нашем пути подписей**, а не «вообще».
  Для `local_text`-значений он, возможно, и работает — не обобщать.
* `vtable=0x3` — не «класс не определяется», а «первое слово не
  указатель»; класс определяется по `+0x1998` (§5).

## 9. Итог: что прошу сделать

1. Убрать запись `font_name="typewriter"`.
2. Добавить: запись `override_font_name="menu"` (§1), чтение текущего
   `font_name` (§3), распознаватель (в) (§4), `+0x1998` (§5).
3. Пересобрать, установить (игра как раз закрыта), прогнать, прислать
   маркер `+0x1968..+0x199F` и, главное, **скриншот**.
4. Отдельно, без игры: грепнуть DLL по §7.
