# A-0036: mod-side пути к кириллице для native Options не найдено — дальше нужен engine font path

## 0. Решение

**Да: можешь переходить к своему EXE-анализу.** Среди доступных mod-side данных и уже проверенных вызовов нет пригодной точки, которая назначает кириллический font object строкам native Options. Значит, собирать ещё один вариант `font_name`, перекодировать байты или менять TTF для этой страницы оснований нет.

Вариант когда-нибудь может быть реализован как **DLL-only код-кейв**, если твой анализ EXE найдёт читаемое поле/вызов установки `Font*` либо способ регистрации engine-шрифта. Сейчас нет ни точного адреса, ни ABI, ни безопасного поля для такого кейва. EXE я не анализировал и не патчил; игровые данные/конфиги тоже не менял.

## 1. Алиас `menu` / добавление собственного font alias — не mod data

По уже разобранному `fonts_ru.bin` (A-0034 §1) имеющиеся engine-алиасы включают:

| алиас | таблица | ресурс |
|---|---:|---|
| `menu` | 271 записей, кириллический charmap | `font\font_metro_for_menu_cyr_ru` |
| `arial` | 256 записей, identity/Latin | `font\font_arial` |

Это данные шрифтового загрузчика игры (`content\scripts\fonts_ru.bin`); в просмотренных mod-side скриптах нет регистрации этого engine alias или font object. `.lng` даёт локализованные строки/charmap, не новый font object. У `kit092/ru/ui2-0.9.2.json` ровно четыре группы — `popups`, `options`, `hints`, `hintpages`; поля `fonts` там нет.

В mod DLL обнаружены четыре **других** ресурса — RCDATA TTF `INFO_BARLOW_CONDENSED_SEMIBOLD` и три `INFO_INTER_*`. `tools/merge_cyrillic.py` добавляет Unicode-глифы в TTF `cmap`; это не 23-байтовый engine `tcmap` и не регистрация alias/resource в `Fonts`. В 0.9.2 patcher (`origin/local/opencode@db7575e:tools/apply_ru_092.py`, строки 160–169) прямо помечает эти ресурсы как неиспользуемые в 0.9.2 пути; `collect_fonts()` определена, но поиск по файлу нашёл только её определение: в проверенной сборочной ветке вызова нет. Ни имя `menu` в `.ru`, ни строка `caption = font\font_metro_for_menu_cyr_ru` в переводных данных сами по себе не регистрируют engine font.

В L-0040 также сообщён runtime scan 6.2 GB без имён `font_arial` / `font_metro_for_menu_cyr_ru` и без исходных 23-байтовых `tcmap` записей. Это не доказывает, как движок преобразует/хранит font object, но не даёт mod DLL готовый объект для копирования. Для нового alias понадобился бы engine-side loader/регистрация полного объекта (таблица метрик + атлас), не строковый alias или TTF из RCDATA.

## 2. Запись опции / UI2 — текстовые данные, не font selector

В постановке L-0041 описана запись 0.9.2 по `0xBA3B0..0xBD9B0` как `{key ptr, key len, caption ptr, caption len, flag}` с регистрацией через `0x4632E0`. В этом описании нет указателя/имени шрифта или style. `flag` не расшифрован как font selector; без DLL-байтов утверждать его скрытый смысл нельзя, поэтому конкретный бит/байт для подмены назвать невозможно.

Независимая проверка UI2-кита:

* JSON содержит только `{index, orig, ru}` для `popups` (16), `options` (82) и `hints` (52); у 14 `hintpages` добавлены `orig_title`/`ru_title`.
* Патчер 0.9.2 задаёт для этих таблиц базы/stride и расположение строк: `popups 0x4EF010/0x70`, `options 0x4F5090/0x20`, `hints 0x4EA538/0x28`, `hintpages 0x4EC490/0x20`. У `popups`/`options` тело хранится парой pointer/length; `hints` — bare body pointer; у `hintpages` пары title/body стоят в `+0x00`/`+0x10`.
* `load_ui2()` (`apply_ru_092.py`, строки 621–707) читает и перенаправляет эти строки. В этой схеме нет поля alias/style/font. Для `popups`/`hints` patcher не декодирует всю непрозрачную запись, поэтому это не заявление о каждом неизвестном padding/флаге: это вывод, что среди известных сериализуемых полей и патча нет font route.

В схеме/definition control встречается строковое property `font_name`; в L-0037 (0.9.1) setter принимал `menu`, но визуального эффекта не было. Code cave вызывал вложенный setter `font_name` **до** передачи исходного `caption` setter-у — то есть это не запись после отрисовки. Это подтверждает, что запись свойства сама по себе не переключает используемый рендером шрифт.

В L-0040 проверка `text_font=menu` была на неверном типе: у option row в его bag нет `text_font`; `set_ok/set_fail` остались нулевыми, поэтому этот прогон не доказывает отказ или успех сеттера. Имена стилей `Text\Font` / `Persona\Font` в L-0040 относятся к text/persona-widget пути; связи этих style slots с дескриптором native option row не найдено. Это не основание назначать `style`/`text_font` записи строки.

Наконец, property schema/definition и живой list-item — разные объекты. В исследовании list-item для 0.9.1 (A-0024/A-0035) у него не было `font_name`/`override_font_name`, а `+0x60` не являлся полем шрифта. Этот layout нельзя переносить на 0.9.2 без DLL/runtime evidence.

Следовательно, в доступном описании menu descriptor нет известного безопасного data-only поля «создай эту строку сразу с `menu`». Изменение property bag не меняет используемый рендером шрифт; гипотетическую привязку именно при конструировании node можно проверить только через engine path.

## 3. Функция «text node + Font*» из mod DLL не обнаружена

Из доступных материалов установлен только путь подписи: копирующий helper вызывается как `call 0x8E80` (L-0039/L-0040), а hook setter-а свойств 0.9.2 стоит на RVA `0xA4C40`. Это передача байтовой строки и запись строкового property, не подтверждённый вызов вида `set_font(text_node, Font*)`.

В `caption_font_hook.py` есть ещё экспериментальный `font_subst`: он сканирует первые `0x100` байт объекта, пришедшего в hook, ищет dword-ref `arial` и при совпадении может заменить его на ref `menu`. Это не общий setter для текстовой ноды. В L-0037 (runtime 0.9.1) такой scan на 259 вызовах не нашёл ни одного ref (`subst_found=0`); дамп показал, что сканировался SSO property bag `mevr_vr`, не объект render-node, а пригодного `local_text` sample не было. Поэтому это не найденное поле text-node и не подтверждённое решение для 0.9.2; оно также не исключает, что нужный ref лежит вне этого bag/диапазона.

Итак, нет ни подтверждённого вызова `set_font(text_node, Font*)`, ни его сигнатуры, ни безопасного поля шрифта, которое можно записать. Именно неизвестный engine вызов/поле нужно найти на твоей стороне; угадывать RVA/ABI здесь было бы опасно.

Доступная в репозитории карта для старой версии — не замена этому анализу: A-0029 описывает 0.9.0 native `SetCaption` и отдельное дерево ImGui; переносить оттуда RVA на 0.9.2 нельзя. Исходных байтов 0.9.2 DLL в текущем Git checkout также нет — доступны patcher/plan/kit и runtime-отчёт L-0040. Поэтому это отрицательный ответ по существующим mod-side интерфейсам, а не заявление, что DLL-кейв принципиально не сможет вызвать найденный тобой engine API.

## 4. ImGui / TTF — отдельная подсистема, не Options menu

`INFO_*` RCDATA TTF и `AddFontFromMemoryTTF` относятся к отдельному ImGui-пути мода; A-0003/A-0029 связывают этот путь с плашкой ссылок (например, “Opened in your browser”, Ko-fi/GitHub и т. п.), а не с нативной Options-страницей. Для этих ImGui-строк замена TTF с добавленным Unicode `cmap` технически подходит при UTF-8-тексте, хотя именно русский runtime-результат в 0.9.2 этими материалами не подтверждён. Запрошенная инструкция `notes/phase2-font-patch.md` в fetched Git tree/history не найдена; оценка основана на `merge_cyrillic.py`, RCDATA/ImGui-маршруте из A-0003/A-0029 и 0.9.2 patcher.

Строки Options (`ДВИЖЕНИЕ`, `ТЕЛО`, `РУКИ`, `ПРИЦЕЛЫ`) не идут через этот ImGui TTF путь: L-0038/L-0040 показывают байтовые подписи, отрисованные identity-`arial`, тогда как рядом game `Esc НАЗАД` рисуется другим шрифтом. `popups/options/hints/hintpages` в 0.9.2 — UI2-таблицы строк, не ImGui-виджеты с полем font. Содержимое 14 страниц `VR HINTS` входит в UI2 `hintpages`; у 0.9.2 patcher `EXTRA_STRINGS=()`, так что отдельный литерал-заголовок `VR HINTS` этой сборкой не классифицирован. Ни один из этих фактов не делает TTF-подмену решением для списка Options.

По ранее заданному продуктовому ограничению ImGui debug overlay и подпись “Opened in your browser” остаются как есть; этот отчёт их не переводит и не предлагает патчить.

## 5. Что остаётся и следующий шаг

* Кодировка charmap уже проходит валидатор и доходит до renderer; оставляем её. Причина видимого Latin/mусора — выбранный font object, не payload.
* В доступном mod-side наборе нет alias-table записи, row-style/font field или вызова установки engine `Font*`, который можно превратить в пригодный к сборке патч.
* **Итог: mod-side data/TTF путь для native Options закрыт; переходи к engine-side анализу.** Ищи default-list draw → источник `Font*`/fallback `arial` и способ назначить готовый `menu`-объект до первого draw (или font setter для text node). Если найдёшь RVA/ABI/поле, его можно будет оценить как DLL-only hook, не меняя файл EXE.
