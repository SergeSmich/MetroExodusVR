# L-0019: bag6 прогон — set_ok=0 (записи `override_font_name` нет), гейт=0, qword `+0x60`=0

## 0. Числа маркера (первый прогон bag6)

```
calls=1254  caption=259  set_ok=0
gate [control+0xac]&1 = 0
qword [control+0x60] = 0x0000000000000000
control=0x817eaeee80  bag=40 записей
caller=module+0x90b47
```

**Главное: `set_ok=0` и в баге 40 записей `override_font_name`
отсутствует.** Значит вложенный сеттер `0x9bc70` не нашёл запись —
и записывать «как в `font_name`» нечего. В том же баге есть
`font_name` kind=2/kind=1 = `menu` (дефолт класса), `caption`, `hint`,
`on_click` и т.д.

## 1. Что это, вероятно, значит

Баг контрола — это **набор только заданных свойств** (kind-2 = заголовок
`choose`, kind-1 = тело с дефолтом), а не полная схема на 705 свойств.
`override_font_name` в него попадает, только если он **есть в
определении элемента**. У мода его нет → сеттер честно возвращает 0.

Отсюда два пути (нужен твой выбор):

* **A. Дописывать запись** (insert в вектор `[obj+0x38..0x40]`) с
  `kind=1, name="override_font_name", value="menu"` — это повторяет
  парсер, но требует знать точный размер записи и владение памятью
  (`[rcx+0x38]` — живой контейнер; рост) — риск крэша;
* **B. Писать прямо в член `[control+0x60]` = пакетная ссылка**
  (статически доказано dword, `mov dword [rdi+0x60]`, дефолт `-1`).
  Тогда надо: взять `0x0025b63` (pack `menu`) и **увеличить refcount**
  `lock inc dword [table + idx*8 + off + 8]`. Это дешевле и без роста
  контейнера. Но `[control+0x60]` — это parse-объект или draw-объект?
  На прогоне он `0` — совместимо и с «пусто», и с «не тот объект».

## 2. Ещё наблюдение (важное для отбора контролов)

Последний пойманный контрол — игровой, не наш: `caption` =
`$hints` (языковой ключ!), есть `on_click_args="hints_menu"`.
То есть хук ловит **все** caption-сеттеры игры (259 штук), и
«последний» — не наш. Для фильтра это подтверждает твой §4: решение
должно приниматься в хуке по содержимому подписи.

⚠️ Сэмпл подписи в маркере при этом прочитался мусором:
`len=32765, sample=b';?7I:h…'`. Значит `[rdi+8]` для **этого** вызова —
не длина `string_view` (или value передан иначе). До исправления сэмпл
не используем; хеш в хуке это обойдёт (считать по фактическим байтам
value, которые сеттер всё равно видит).

## 3. Что прошу решить (A-0019)

1. **Путь A (insert) или B (dword `+0x60` + refcount)?** Мой голос — B:
   меньше риска, статически доказано (`mov dword [rdi+0x60]`), а
   refcount-таблица у нас уже разобрана в `L-0015 §1.1`. Если B — скажи,
   какой объект считать «тем»: в маркере есть только parse-объект
   (`control=0x817eaeee80`); если он же и рисует, B закрывает задачу.
2. Если B: подтверди, что писать надо `0x0025b63` (pack `menu`) и что
   gate `[+0xac]&1` к отрисовке не относится (он завязан на parse —
   в `0xc46cb0` стоит перед каждым чтением свойства).
3. Если B «не тот объект» — назови, как найти draw-копию (ты уже
   предлагала сравнить `+0x60` в двух объектах, §3.3 A-0017).
