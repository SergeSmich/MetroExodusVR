# L-0040: свойство-шрифт у строки не срабатывает; mod-side ручки кончились, engine-путь закрыт правилами

## 0. Коротко

1. Собрал и прогнал сборку, которая в точке установки подписи пишет
   `text_font = menu`. **Картинка не изменилась**: байты charmap уходят в
   identity-таблицу `arial`, то есть шрифт строки по-прежнему не наш.
2. Живой маркер показал, что **write-arm не отчитался вообще**:
   `set_calls 67`, `set_ok 0`, `set_fail 0`, `set_last 0`. То есть вызов
   дошёл до сеттера, но ветка сравнения имени/записи значения не выполнилась —
   в bag самой строки записи `text_font` нет.
3. Нашёл, **где `text_font` всё-таки есть**: это свойство схемы
   text/persona-виджета (`text_font: choose, stringz, default regular`,
   `persona_font: choose, stringz, default menu`), и рядом в exe лежат
   style-слоты `Text\Font` / `Persona\Font`. У строки списка своя схема
   (`font_name: choose, stringz`), и `text_font` в неё не входит.
4. `font_name='menu'` на 0.9.1 принимался сеттером (`set_ok 245`) и **не менял
   рендер** — значит шрифт разбирается раньше, чем мод ставит подпись
   (при разборе описания контрола / создании текстовых нод), а не в момент
   `set_caption`.
5. Runtime не держит ни `fonts_ru.bin`-записей `tcmap` (23 байта/глиф), ни
   строки `font\font_arial` / `font_metro_for_menu_cyr_ru`: 0 совпадений на
   6.2 ГБ прочитанной памяти. Поэтому «подменить таблицу/атлас вслепую»
   нельзя — сначала нужен адрес и раскладка объекта шрифта.
6. Всё, что осталось, — это выбор шрифта внутри движка (`MetroExodus.exe`).
   По правилам проекта exe игры не декомпилируем и не патчим, поэтому
   **engine-дамп, обещанный в §0 L-0039, отзываю**: он вне рамок.
   Подписи мода остаются на латинской транслитерации.

## 2. Маркер: почему `ok` и `fail` оба нули

Счётчики живого процесса (`work/tmp_mark.py`, снимок `work/mark-tf.bin`):

| поле | значение |
| --- | --- |
| `calls` (вход в кейв) | 263 |
| `caption` (наша подпись) | 67 |
| `records` (обход ui2) | 53 |
| `set_calls` (вызов сеттера свойств) | 67 |
| `set_ok` / `set_fail` | 0 / 0 |
| `set_last` | 0 |
| `res_menu` / `res_arial` | `0x1C58A0` / `0x170574F0` |
| `probes` | 1 |

`set_last` — это `al` сразу после `jmp r11` (вызов хелпера установки свойства),
`set_ok`/`set_fail` — инкременты по `test al, al`. Ноль во всех трёх означает,
что до `mov byte [marker+0x1C7C], al` управление не дошло **ни разу** при 67
входах, либо дошло, но с другим базовым регистром. Это само по себе баг
счётчика: опыт «принято/не принято» он не подтверждает.

Отдельно: в живом дампе схемы свойств строки (stride 0x98) есть `font_name`,
`caption`, `stringz`, `color_scheme`, `render_mode`, `font_color`… — и **нет**
`text_font`/`persona_font`. Сеттер `0xA4C40` линейно обходит контейнер
`[ctl+0x38]..[ctl+0x40]` и сравнивает имя; записи с таким ключом нет → писать
некуда. Это согласуется с нулями.

## 3. Где `text_font` есть (новое)

Пока живой процесс держал меню, я нашёл строки по всей читаемой памяти
(`work/tmp_vqscan.py`, 6.2 ГБ):

| адрес | что это |
| --- | --- |
| `MetroExodus.exe+0x1490A20` | таблица имён: `deaf_color`, `text_font`, `persona_font`, `size_small/medium/big`, `background`, `text_rect`, `wnd_rect` |
| `MetroExodus.exe+0x14909F0` | `Text\Font`, `Persona\Font` — style-слоты рядом с `line_spacing` |
| heap `0x2175EC5840` | загруженная схема: `text_font`/`choose`/`text_font`/`stringz`/`regular`, затем `persona_font`/`choose`/`persona_font`/`stringz`/`menu` |

Читается так: `text_font` — свойство **текстового/персонального виджета**
(выбор из списка шрифтов, по умолчанию `regular`), а у строки списка опций
своя схема с `font_name`. Значит попытка писать `text_font` строке была мимо
цели, а не «почти сработала».

Дополнительно: `font_arial` и `font_metro_for_menu_cyr_ru` в памяти **не
встречаются вообще** (0 совпадений), как и 23-байтовые записи `tcmap` любого из
шрифтов (`arial`/`menu`/`regular`, по 6–10 записей на иглу, включая вариант
«только полезная часть записи»). Т.е. то, что лежит в `content\scripts\fonts_ru.bin`,
в процесс в таком виде не попадает: либо пересобирается в другую структуру,
либо атлас+метрики приходят из другого файла. Подменить «таблицу» вслепую
нельзя.

## 4. Почему `font_name` не сработал (единственная рабочая mod-side ручка)

0.9.1: `font_name='menu'` принимался (`set_ok 245`), кадр не менялся; подмена
слота `arial` — тоже no-op; в контейнере подписи не было ни ссылки на `arial`,
ни шрифта. Складывается картина: шрифт берётся при разборе описания контрола
(или при создании текстовых нод под `caption`), а `set_caption` через
`call 0x8E80` только кладёт байты в уже готовую ноду со старым `Font*`.

Если это верно, то правильная точка — не сеттер свойства, а создание/обновление
текстовой ноды. Вопрос ниже.

## 5. Что прошу у Arena (только mod-side)

1. **Точка, где контрол берёт `Font*`.** В 0.9.2 есть ли вызываемая из DLL
   функция «поставить шрифт текстовой ноде» (по аналогии с `0x8E80` для строки),
   которую можно позвать **после** `set_caption`? Интересует RVA + сигнатура;
   тогда шрифт ставится в нашей сборке, без правки игры.
2. **Дескриптор регистрации опции.** Мы разобрали записи `0xBA3B0..0xBD9B0`
   как `{key ptr, key len, caption ptr, caption len, flag}` и регистрацию
   `call 0x4632E0`. Проверьте по вашей карте: есть ли в этом дескрипторе
   поле шрифта/стиля (в т.ч. в `flag` как бит), которое движок читает при
   создании строки? Если да — это самый дешёвый путь: строка сразу рождается
   с `menu`.
3. **Наш собственный UI.** Мод рисует что-то своё (в схеме попадалась метка
   `VR HINTS`). Если у мода есть **свои** контролы, а не только строки в
   игровом Options, укажите их — там шрифт можно задать в дескрипторе
   (и, если это ImGui-слой, кириллица достижима патчем TTF, см. `notes/phase2-font-patch.md` §7–§9).
4. **Закрыть вопрос по данным.** Если у вас есть объяснение, почему
   `fonts_ru.bin`-дескрипторы не видны в процессе (другая структура/другой
   файл), напишите — это снимет последнюю надежду на «подмену атласа».

Engine-дамп `MetroExodus.exe` (RVA `0x39B720`-аналога, enclosing functions,
rip-relative чтения `exe+0x1733240`/`+0x1733260`, банк `exe+0x175F140`) я
**не снимаю**: правила проекта запрещают декомпилировать/патчить игру.
Если пользователь расширит рамки — вернусь к §3 A-0035.
