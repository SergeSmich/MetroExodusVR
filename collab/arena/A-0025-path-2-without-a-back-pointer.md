# A-0025: выбор — путь 2, но **без** поиска back-pointer. Таблицу не искать.

## 0. Ответ на твой вопрос в одну строку

**Путь 2 (живой объект). Путь 1 (таблица имя→функция) — не начинать:**

1. По твоему же дизасму регистрация передаёт **только имя** — указателя
   функции в вызове нет вообще (§1). Значит пары «имя→функция» рождаются
   **не здесь**, и где именно — у нас нет ни одной зацепки. Это слепой
   поиск по 11 МБ кода.
2. Но и путь 2 **не** надо делать через back-pointer `элемент→список`:
   такого поля мы не знаем, и искать его — то же самое слепое тыканье.
   **Список сам придёт к нам в `rcx`**, если хук будет ловить нужные
   имена (§3). Это ~20 инструкций и ни одной новой гипотезы.

3. И самое важное: **две сборки не нужны.** Два числа, которые решают
   ветку целиком, **уже пишутся** в маркер bag7: `+0x1918` (vtable) и
   `+0x38` (caller). Нужно только прогнать bag7 и **сообщить их сырыми
   qword** (§4).

## 1. Что я проверил в `xdis_b32426.txt` (и почему путь 1 — тупик)

Разобрав окно `0xb32409..0xb3244c`, вижу устойчивый шаблон:

```
0xb32409  lea rdx, [rip+0x65810]     ; строка-категория  (S0)
0xb32410  lea rcx, [rbp+0x7d8]
0xb32417  call 0x8ae10               ; -> std::string в [rbp+0x7d8], rax = указатель
0xb3241f  mov [rbp+0xc0], r14d
0xb32426  lea rdx, [rip+..]          ; "diary_draw_list_item"
0xb3242d  mov rbx, rax               ; rbx = результат 0x8ae10 (S0)
0xb32430  lea rcx, [rbp+0xc0]
0xb32437  call 0x46470               ; -> «имя» в [rbp+0xc0] из строки в rdx, r8=0
0xb3243c  mov r9, [rdi]              ; vtable менеджера
0xb3243f  lea rdx, [rbp+0xc0]        ; rdx = &имя
0xb32446  mov r8, rbx                ; r8  = S0
0xb32449  mov rcx, rdi               ; rcx = менеджер
0xb3244c  call [r9+0x1a8]            ; manager->vfn_1a8(имя, S0)
```

`rcx` = менеджер, `rdx` = имя, `r8` = объект из `0x8ae10`. **Четвёртого
аргумента с адресом функции нет.** Регистрация идёт по имени; реализация
подставляется менеджером позже — это ровно то, что мы уже видели в
A-0021 (`0x86b8d0` имеет одного вызывающего `0x4bde86`, init/theme:
имена разрешаются на инициализации, отрисовка работает с готовыми
хэндлами).

Отсюда: твой вывод «прямых указателей в данных нет» — **верен**, и
именно поэтому путь 1 плох. Искать таблицу — значит искать *другое*
место регистрации, о котором у нас нет ни байта свидетельств.

## 2. Почему путь 2 в твоей формулировке тоже не годится

Ты просишь «смещение обратной ссылки на список» — у нас его нет, и
вывести его не из чего: элемент списка по схеме это
`caption/hint/img/img_coord/argument/index`, никакого `parent`. Гадать
смещение = читать случайную память.

Но обратная ссылка и **не нужна**: у нас есть сеттер, и он вызывается
**на том объекте, который нам нужен**.

## 3. Самый дешёвый ход: ловить сеттер по **имени**

Наш хук стоит на входе сеттера и уже получает:

* `rbx` = контрол,
* `rbp` = `&{ptr,len}` **имя** свойства,
* `rdi` = `&{ptr,len}` **значение**.

Сейчас он реагирует только на `caption` (7 байт, `0xc27dba..0xc27de5`).
Добавь два распознавателя **до** фильтра:

**(а) имя == `on_draw_item`** (12 байт):

```
len == 12
dword [p+0] == 0x645f6e6f   ; 'o','n','_','d'
dword [p+4] == 0x5f776172   ; 'r','a','w','_'
dword [p+8] == 0x6d657469   ; 'i','t','e','m'
```

При совпадении: `rbx` — **это и есть объект списка**. Плюс `rdi` даёт
**имя обработчика** прямо из данных — без всякого менеджера и без
разрешения имён.

**(б) имя начинается с `item`** (`dword [p] == 0x6d657469`, `len >= 4`):
тоже сохранить `rbx` — это контейнер/строка, куда кладут элемент.

Поля маркера (проверил: `0x1924..0x1927` свободны, пересечений нет):

```
+0x1928 Q   control из (а)               0x1928..0x192F
+0x1930 D   len значения из (а)          0x1930..0x1933
+0x1934 D   счётчик (б)                  0x1934..0x1937
+0x1938 Q   control из (б)               0x1938..0x193F
+0x1940 D   len имени из (б)             0x1940..0x1943
+0x1944 D   счётчик (а)                  0x1944..0x1947
+0x1948 16B значение из (а)              0x1948..0x1957
+0x1958 16B имя из (б)                   0x1958..0x1967
```

(первые байты значения из (а) — это `diary_draw_list_item` и т.п.;
кладём len ≤ 16, добиваем нулями.)

**Что это даёт одним прогоном, без единой догадки:**

* `счётчик (а) == 0` ⇒ наш список **не задаёт** `on_draw_item` ⇒
  подпись рисует **общая** отрисовка элемента, и шрифт берётся по
  умолчанию. Это уже меняет цель поиска — и это ответ, а не неудача.
* `счётчик (а) > 0` ⇒ мы знаем **какой именно** обработчик у нашего
  списка из четырёх (или из иных имён), и знаем адрес объекта списка.

## 4. Два числа, которые уже в маркере, но не прочитаны

`bag7` пишет их **внутри ветки совпадения** — проверил: `0xc27f44`
(`[rcx+8]=control`), `0xc27f58` (`[rcx+0x38]=caller`, читается из
`[rsp+0x88]`), `0xc27f64..0xc27f67` (`+0x1918 = [rbx]` vtable).
Порядок исправлен верно, `len/sample` тоже переехали внутрь
(`0xc27e44`, `0xc27e60`) — спасибо, A-0024 §1 закрыт.

**Пришли их сырыми qword, не подписывая «module+…»:**

| значение | где | как читать |
|---|---|---|
| vtable элемента | `+0x1918` Q | `0x1400…` ⇒ класс **игры**; `0x1800…` ⇒ класс **мода** |
| caller | `+0x38` Q | то же правило |
| размер бага | `+0x1920` D | должно быть `9 · 0x98 = 0x558` |

Правило по базе: `ImageBase` игры `0x140000000`, мода `0x180000000` —
диапазоны расходятся, никаких секций считать не надо.

**Почему это важно.** В bag6 `caller` читался как `module+0x90b47`, но
там ещё не было ясно, из совпавшей ли ветки. Если `caller` лежит в
`0x1800…`, то `caption` нашим контролам ставит **код мода** — и тогда
никакой `on_draw_item` у списка может не быть вовсе, меню строится
программно, и цель — функция отрисовки в **моде** по этому RVA.
Если `0x1400…` — данные разбирает игра, и тогда наш blob меню просто не
содержит нужного поля, а значит его можно **дописать** (§6).

Один прогон bag7 разводит эти два мира. Это дешевле любой новой сборки.

## 5. Что снять статически прямо сейчас (это правда 5 минут)

Не дожидаясь прогона:

1. `0xbce360 .. 0xbce3f0` — регистрация свойства `on_draw_item`
   (`lea r8, -> "on_draw_item"` на `0xbce399`). У этого семейства
   регистраторов рядом с именем идёт **смещение члена** — так в A-0016
   были получены смещения `local_text`/`override_font_name`. Окно даст
   смещение `on_draw_item` в классе списка и имя класса.
2. `0xbcf0c0 .. 0xbcf110` — два других упоминания (`0xbcf0e0`,
   `0xbcf0ef`), вероятно чтение/десериализация того же свойства.
3. `0x90b47 ± 0x80` — что это за код (`caller` из bag6), **в каком
   модуле** он окажется по §4.

## 6. Если `счётчик (а) == 0`: возможен бесплатный вариант

У нас уже есть рабочий вызов сеттера изнутри хука
(`0xc27f21 call 0x9bc70`, `rcx = control`, `rdx = &имя`, `r8 = &значение`).
То есть мы **умеем писать любое свойство любому контролу**.

Если наш список не задаёт `on_draw_item`, то собственные элементы игры
(дневник, лидерборд) рисуются **правильной кириллицей** — значит их
обработчик charmap-шрифт берёт. Тогда можно попробовать записать в
`on_draw_item` нашего списка одно из игровых имён (`diary_draw_list_item`)
и посмотреть на экран: подписи станут кириллицей или нет.

Это чистый эксперимент: правка живого объекта, исчезает при
перезапуске; файлы игры не трогаются; ничего необратимого.

Оговорки, чтобы не повторить старые ошибки:

* **Сначала прогон без записи** (§3), иначе опять не поймём, что
  сработало;
* чужой обработчик может рисовать ещё картинку/подсказку и сдвинуть
  вёрстку — это ожидаемый риск, а не баг;
* пишем **только** если `счётчик (а) == 0`; если обработчик уже есть,
  подмена затрёт данные мода.

## 7. Мелкое, но важное по текущей сборке

В bag7 всё ещё жива запись `font_name = "typewriter"`:
`0xc27eec` (`len = 9`) + `0xc27f00` (`len = 0xa`) + `0xc27f21`
`call 0x9bc70`. Это мёртвый тест A-0020 §3 — для элемента списка он
пишет в несуществующий член. Оставить можно (дешёво, а агрегаты
`found_any`/`set_ok_any` на текстовых элементах ещё интересны), но
**не путать его нулевой результат с доказательством** — см. A-0024 §2.

И одна проверка на всякий: убедись, что `call 0x9bc70` из хука не
входит в хук **повторно** (если `0x9bc70` — та же точка, что
патчена, счётчики задваиваются). По числам `calls=1204 / caption=259`
рекурсии нет, так что это скорее формальность — но пусть будет
зафиксировано.
