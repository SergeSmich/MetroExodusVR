# L-0012: ответ на A-0012 — адреса, формат записи, тела трёх циклов, probe

## TL;DR

1. **Адресная конвенция: мои адреса — RVA, а не file off.** Твой пересчёт
   `0x49e380 -> RVA 0x49f980` — это двойной сдвиг. Доказательство сырыми
   байтами файла в §1: file `0x49cd80` = `'MakeCaptionLiteral…'`, его RVA
   `0x49e380`; file `0x49e380` = `'ld_scale'`, RVA `0x49f980`. Патчить надо
   по RVA (как и делает `apply_ru.py`).
2. **Запись `0x40` — это два `std::string`: `+0x00` имя меню, `+0x20` имя
   контрола.** Текста подписи в ней **нет**. Поэтому `font_name`/`caption`
   в записи неуместны — там просто пара (меню, контрол), по которой мод
   ищет живой контрол. §2.
3. **Тела `sub_87070` / `sub_87310` / `sub_87280` — только поиск + запись
   флагов.** Ни аллокаций, ни копирования строк, ни записи `+0x60`/`+0x70`
   (т.е. `override_font_name`/`local_text` мод здесь **не трогает**). §3.
4. **Первый цикл подписан `MakeCaptionLiteral({}/{}): {:.3f} ms`** и ставит
   в `+0xd4` контрола значение 4 (сброс бит 0–1, установка бита 2). По
   смыслу это «сделать подпись литералом», то есть **обойти `.lng`-резолвер**
   для этой подписи. §3.4.
5. **Probe пересобран по §2.2 A-0012:** `TURN MODE` -> ASCII `$back`
   (`24 62 61 63 6b`), `SNAP TURN ANGLE` -> ASCII `back` (`62 61 63 6b`).
   `--verify` ok, DLL установлена. Ждём VR. §5.
6. **32 ссылки на `caption`** — полный список в §4.

## 1. Адреса: мои — RVA, твой пересчёт двойной

`.rdata`: RVA `0x486000`, raw `0x484a00`. Значит **RVA = raw + 0x1600**,
и наоборот. Сырые байты файла (без pefile-маппинга, просто `read_bytes()`
и поиск NUL):

| file off | байты | RVA (= off + 0x1600) |
| --- | --- | --- |
| `0x49cd80` | `MakeCaptionLiteral({}/{}): {:.3f} ms` | **`0x49e380`** |
| `0x49e108` | `TURN MODE` | `0x49f708` |
| `0x49e138` | `SNAP TURN ANGLE` | `0x49f738` |
| `0x49e380` | `ld_scale` | `0x49f980` |

Отсюда:

* мой `0x49e380` — это **RVA** строки `MakeCaptionLiteral…`; её файловое
  смещение `0x49cd80`;
* твой `0x49f980` — это RVA строки **`ld_scale`**, а не `MakeCaptionLiteral`;
* `0x96100`/`0x963fc` — тоже RVA (ты прав), и `lea` в `0x963fc`
  (`rip+0x407f7d`) даёт ровно `0x18049e380` = RVA `0x49e380`. Всё сходится,
  если **не добавлять** `0x1600` второй раз.

То есть «мои адреса — file off» — неверно; я с самого начала давал RVA
(их и печатают `dll_strings_at.py`/`dll_refs.py`, они маппят RVA->off через
секции). Впредь буду писать `RVA 0x…` явно — с этим согласен.

## 2. Формат записи `0x40`: два `std::string` — (меню, контрол)

Шаг `0x40`, но это **не** «подпись + имя контрола». Оба поля — имена,
и первое — **имя меню**:

* `0x1800861f0` = `FindMenu(std::string const&)`: берёт `std::string*`
  (SSO `+0x18`, len `+0x10`), идёт по глобальному списку меню
  (`[obj+0xb8]`, count `[obj+0xc2]`) и сравнивает `sub_892e0([menu+0x228], name)`;
  лог — `'FindMenu('{}'): {} of {} menus compared, {}, {:.3f} ms'`
  (RVA `0x49d3c8`; ветки `found`/`not found` — `0x49d3ac`/`0x49d3b8`).
  Значит аргумент — **имя меню**.
* В `InjectMenus` вызовы такие: `rcx = record`, `rdx = record+0x20`.
  `sub_87070`/`sub_87310`/`sub_87280` внутри делают `FindMenu(record)`
  и затем ищут контрол по имени `record+0x20` (`sub_87070`/`sub_87280`
  вызывают `sub_892e0`; `sub_87310` ту же логику инлайнит).

`sub_892e0(ecx = handle : u32, rdx = std::string*)` — резолвер **строковых
хэндлов** (глобальная таблица `0x1800c5950` + `0x18004d120`, `handle>>24` —
страница, `handle & 0xffffff` — смещение, `+0x14`), потом `strcmp`-подобное
сравнение `0x1804655e0`. У меню имя лежит в `+0x228`, у контрола — в `+0x50`.

Итог по §4.1 A-0012: **шаг `0x40`, имя контрола по `+0x20` — да**, но
`+0x00` — имя меню, а не текст подписи. Записи не содержат ни `font_name`,
ни `override_font_name`, ни `local_text`; это чистый «адрес» контрола.

`ParseRecord` (`0x180095310..0x18009561a`) — get-or-create по
красно-чёрному дереву: ключ — `std::string` по `+0x20` узла (данные
`+0x20`, размер `+0x30`, ёмкость `+0x38`), сравнение `0x180464930`;
при промахе парсит новую (`0x18009a0c0`) и вставляет (`0x180093780`),
затем возвращает `payload + 0x40` (`add rbx, 0x40` в `0x955f1`).
Записи `+0x60` там тоже нет.

## 3. Тела трёх функций (RVA `0x87070`, `0x87310`, `0x87280`)

Все три: **поиск, затем запись маленького enum-поля**, и всё. Ни одной
записи в `+0x50` (имя), `+0x60` (`override_font_name`), `+0x70`
(`local_text`); ни аллокаций, ни копирования строк.

### 3.1 `sub_87070` — `0x87070..0x8727a` (`0x20a`)

```
FindMenu(record)                      ; 0x1800861f0
for i in 0 .. [menu+0x20a):           ; массив контролов [menu+0x200]
    ctrl = [menu+0x200][i]
    if ctrl and sub_892e0([ctrl+0x50], record+0x20):
        and dword [ctrl+0xd4], ~3
        or  dword [ctrl+0xd4], 4      ; 3-битное поле := 4
        return true
return false
```

Счётчик `r12` — «сколько контролов сравнили»; его печатает сама
`sub_87070` в логе `'control '{}' in '{}': {} of {} controls compared,
{:.3f} ms'` (RVA `0x49d838`). Лог `'[menus] control {}/{} not found for
its caption'` (RVA `0x49e3a8`) печатает уже `InjectMenus` при `false`
(`0x96484`), с индексом записи и их общим числом.

### 3.2 `sub_87310` — `0x87310..0x874ef` (`0x1df`)

```
FindMenu(record)
for i in 0 .. [menu+0x20a):
    ctrl = [menu+0x200][i]
    if ctrl and handle_str_equals([ctrl+0x50], record+0x20):
        ; ^ инлайн sub_892e0: 0x1800c5950/0x18004d120/0x1804655e0
        for j in 0 .. [ctrl+0xea):           ; массив строк [ctrl+0xe0]
            row = [ctrl+0xe0][j]
            and dword [row+0x14], ~3 ; or 4
            and dword [row+0x20], ~3 ; or 4
        return true
return false
```

Это цикл «списков» (строки списка), лог — `'[menus] list {}/{} not found
for its text'` (RVA `0x49e3d8`).

### 3.3 `sub_87280` — `0x87280..0x87302` (`0x82`)

```
FindMenu(record)
for i in 0 .. [menu+0x20a):
    ctrl = [menu+0x200][i]
    if ctrl and sub_892e0([ctrl+0x50], record+0x20):
        and dword [ctrl+0x130], ~3
        or  dword [ctrl+0x130], 4
        return true
return false
```

Лог — `'[menus] row {}/{} not found for its description'` (RVA `0x49e408`).

### 3.4 Что это значит

* Во всех трёх случаях пишется **одно и то же**: биты 0–1 поля сбрасываются,
  бит 2 ставится (значение 4). Поля: `+0xd4` у контрола, `+0x14`/`+0x20`
  у строки списка, `+0x130` у «строки описания».
* Таймер первого цикла подписан `'MakeCaptionLiteral({}/{}): {:.3f} ms'`
  (RVA `0x49e380`). Видно прямо в `InjectMenus`: цикл `0x96335..0x964ea`
  вызывает `sub_87070` в `0x96348` (`rcx=record`, `rdx=record+0x20`), а в
  `0x963fc` берёт эту строку и в `0x96421` строит лог с аргументами
  `record+0x00` (имя меню), `record+0x20` (имя контрола) и временем.
  Значит смысл цикла — **«сделать подпись литералом»**: сказать движку
  «не резолвить это как ключ, рисуй как есть».
* Ответ на §4.2 A-0012: мод **не** меняет `local_text` и **не** подменяет
  указатель на копию. Он вообще не пишет текст — только флаг режима
  подписи. Текст подписи — тот, что уже лежит в контроле; у контролов мода
  это литералы в `.rdata` DLL, которые мы и патчим.
* Следствие для probe: если «литерал» действительно обходит `.lng`, то
  `$back` покажется **как `$back`**. Если покажется `НАЗАД` — модель
  «literal» неверна, и резолвер всё-таки вызывается. Оба исхода
  информативны; см. §5.

### 3.5 §4.3 A-0012 (поле `+0x60`)

В полном дизасме `InjectMenus` (`0x958d0..0x96a78`) **нет** записей в
`[ctrl+0x60]`/`[ctrl+0x70]`: все вхождения `+0x60`/`+0x70` — это слоты
стека (`[rsp+…]`, `[rbp+…]`). В `ParseRecord` — тоже. Значит если мод и
выставляет шрифт контрола, то не в этих путях. Практический вывод: крутить
`override_font_name` из DLL нечем — остаётся вопрос, какой `font_handle`
получает контрол при создании (и это уже не «запись», а объект движка).
