# L-0006: EN-прогон сделан — модель «`menu`» опровергнута, подписи локаль-независимы

## TL;DR

Один и тот же билд (`MetroExodusVR.probe3.dll`, charmap) прогнан в **двух
локалях игры**. Подписи мода отрисованы **одинаково**:

| Локаль | Низ экрана | `ИГРА` | `ГРАФИКА` | `ТЕЛО` |
| --- | --- | --- | --- | --- |
| RU | `Esc НАЗАД` | `DOH5` | `OH5nD@5` | `:IP?` |
| EN | `Esc BACK` | `DOH5` | `OH5nD@5` | `:IP?` |

Отсюда: **шрифт подписей мода локалью не управляется.** Модель из `L-0002`
§5 (в RU `menu` не резолвится → fallback; в EN `menu` → US-шрифт → `PJ/`)
**неверна** и снимается. `menu`-дыра в `fonts_ru.bin` остаётся реальным
фактом о данных игры, но причиной `DOH5` она не является.

Дополнительно: `PJ/` из `ru/ENCODING_NOTES.md` §1 **не воспроизводится ни в
RU, ни в EN**. Похоже, это наблюдение из другого билда/мода, а не из 0.9.0
charmap. §1 надо править.

## Что видно на скриншотах (подробно)

RU-прогон (нижняя подсказка кириллицей `Esc НАЗАД`):

* `DOH5` — заголовок `ИГРА`;
* `OH5nD@5` — `ГРАФИКА`;
* `:IP?` — `ТЕЛО`;
* строки-полосы между ними **пустые**.

EN-прогон (нижняя подсказка латиницей `Esc BACK`):

* те же `DOH5`, `OH5nD@5`, `:IP?` — **байт-в-байт те же глифы**;
* те же строки-полосы теперь заполнены `???????? …` (широкий ряд
  вопросительных знаков).

## Что это значит про строки-полосы (отдельный симптом)

`?` — типичный признак «charmap-индекс вне таблицы шрифта». В EN на эти
элементы приходит **RU-индекс** (271-записная таблица), а шрифт US
(203 записи) его не находит → `?`. То есть **эти** элементы идут
**локаль-зависимым charmap-путём** — ровно как игровые подписи.

В RU те же элементы пустые. Это не «кириллица невидима», а другой дефект
(возможно, эти строки рисуются шрифтом, у которого нет нужных глифов, и
глиф не подставляется). **Прошу не смешивать это с подписями**: у подписей
поведение ровно противоположное — оно одинаково в обеих локалях, значит
шрифт у них **фиксированный, не из locale-таблицы**.

## Уточнённая модель

| Что | Шрифт | Порядок | RU | EN |
| --- | --- | --- | --- | --- |
| Игровые подписи/значения | locale-таблица (`fonts_ru`/`fonts_us`) | RU-charmap / US-charmap | кириллица | латиница |
| Строки-полосы (этот дефект) | locale-таблица | RU-charmap | пусто | `?` |
| **Подписи мода (caption)** | **один и тот же в обеих локалях** | **identity / Latin-1** | `DOH5` | `DOH5` |
| Проба `0x80..0xFF` | тот же, что у caption | — | пусто | тофу-квадраты |

Три факта про шрифт подписей, которые надо объяснить одновременно:

1. ASCII-диапазон рисуется 1:1 (`0x44`→`D`, `0x4F`→`O`, `0x35`→`5`);
2. `0x80..0xFF` — **нет глифов** (тофу в EN, пусто в RU);
3. выбор шрифта **не меняется** при смене локали.

Пункты 1+2 = шрифт с таблицей на 256 записей в порядке кодпоинтов, у
которой реально заполнены только ASCII-глифы. Пункт 3 = этот шрифт не
входит в locale-набор.

## Кандидаты (проверяемые по `fonts_*.bin`)

Локаль-независимые алиасы — те, у которых **одинаковый путь в RU и US**:

```
console          -> font\font_console
nixie            -> font\font_nixie
symbols          -> font\font_symbol
symbols_durango  -> font\font_symbol_durango
symbols_ps       -> font\font_symbol_ps
arial            -> font\font_arial
editor_symbols   -> ui\ui_font_symbols
small            -> ui\ui_font_hud_01
```

Плюс два алиаса **без пути в обеих локалях**: `stats`, `typewriter`.
`arial` — самый вероятный дефолт текстового элемента (и он же объясняет
«256 записей, заполнен только ASCII»: это растровый Arial-атлас игры,
а не локализованный menu-шрифт).

**Это гипотеза, а не факт.** Нужна статика: какое имя шрифта попадает в
поле элемента, который создаёт мод.

## Что прошу у Arena (обновление приоритетов)

1. **Отбросить поиск `menu`-fallback** — EN-прогон его убил.
2. Найти в `0x9b3a0` (AVER-парсер) / `0x91440` (копия записи 0x1e8) /
   `0x958d0`, **какое значение поля `font_name` получает caption-элемент**,
   если мод его не задаёт. Интересует: есть ли в конструкторе текстового
   элемента **константа-указатель** на имя шрифта (не строка в `.rdata`, а
   указатель на уже существующую строку в данных пакета).
3. Если поле пустое — какой алиас подставляет exe по умолчанию для
   текстового элемента. Кандидаты выше, в первую очередь `arial`.
4. Оценить тот же патч, что и раньше, но с новой мотивацией: проставить
   caption-элементу `font_name = "main_menu"` (RU 271, кириллица) —
   **независимо от локали**, потому что `main_menu` резолвится в
   `font_metro_for_menu_cyr_ru` только в RU, а в EN это отдельный вопрос.
   Для RU-релиза этого достаточно.

## Зацепка в коде (для Arena, из `work/crops/mcl.asm`)

Рядом с проходом установки подписей есть ровно один виртуальный вызов,
похожий на «присвоить текст»:

```
0x96854  mov  rcx, [rbp+0x1d8]      ; this = объект элемента
0x9685b  test rcx, rcx
0x9685e  je   0x9687a
0x96860  mov  rax, [rcx]             ; vtable
0x96863  lea  rdx, [rbp+0x1a0]       ; std::string (SSO на стеке)
0x9686a  cmp  rcx, rdx
0x9686d  setne dl                    ; dl = string is heap-allocated
0x96870  call [rax+0x20]             ; кандидат: SetCaption(std::string)
```

* `[rbp+0x1a0]` — собранная строка подписи; раньше `[rbp+0x1d8]` получает
  `&[rbp+0x1a0]` в `0x95ee3`, то есть это локальный объект/адаптер, а не
  заранее существующий виджет.
* Мод **не** вызывает ничего похожего на `SetFont`: в этой функции нет
  второго виртуального вызова с тем же `this`.
* Значит шрифт берётся из **самого элемента меню** (поле `font_name`),
  которое мод не заполняет, либо из клона/шаблона, откуда элемент создан.

Это согласуется с локаль-независимостью: дефолт текстового элемента —
фиксированный (кандидат `arial`), а не locale-таблица.

## Следствия для перевода

* Кириллица по-прежнему достижима, но **только** через смену шрифта
  caption-элементов. Кодировка/шрифты мода тут ни при чём — подтверждено
  вторым прогоном.
* `ENCODING_NOTES.md` §1 (`ВКЛ → PJ/`) — надо исправить: в 0.9.0 charmap
  такого нет ни в RU, ни в EN.
* `fonts_ru.bin`/`fonts_us.bin` не трогаем (game-data).
