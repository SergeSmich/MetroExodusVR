# A-0019: `0x4ed40` — void и это assert, а не дескриптор; слот `+0x60` регистрируется в менеджере

## 0. Коротко

1. **`+0x60` = dword, подтверждено** — и я записал это в
   `ru/ENCODING_NOTES.md` **§8** (новый раздел), как ты просил: формат
   ссылки, доказательства, последствия по refcount, разница `-1` vs `0`.
2. **`0x4ed40` возвращает `void`.** Эпилог `0x4eef9..0x4ef11` не
   устанавливает `rax` перед `ret` и нет out-параметра. Значит **не
   дескриптор**. По телу это **assert**: строит две временные строки через
   `0x4f100`, сравнивает их с `name`/`hint` байтовым циклом, при
   несовпадении пишет через `0x47b80` с форматом, потом освобождает
   строки. См. §1.
3. **Из этого следует, что мой `A-0018 §3` неверен — отзываю.** Я называл
   функцию вокруг `0xc47077` «кандидатом №1 на резолв шрифта». Твоё
   «это parse, не draw» — правильно.
4. **Побочный, но ценный вывод:** эти два «лукапа» — два **assert**а,
   по одному на `choose` и `_default`. То есть **парсер проверяет обе
   под-записи отдельно**, что независимо подтверждает compound-структуру
   из `A-0015 §2` (1777 `choose` + 1777 `stringz`). Три уровня сошлись:
   схема, `cmp byte [rbx],1` в сеттере, и теперь — asserts парсера.
5. **Новое и важное:** в десериализаторе, сразу после записи ссылки в
   `+0x60`, слот передаётся **виртуальному методу `[vtbl+0x130]`** —
   `lea r8, [rdi+0x60]` (`0xc471e0`). Значит слот **регистрируется в
   глобальном менеджере**. Это объясняет, почему писать напрямую нельзя,
   и даёт второй риск: менеджер может **перезаписать** нашу ссылку при
   перезагрузке. §2.
6. **Главное, что надо закрыть до VR:** доказать, что у `[obj+0x60]`
   есть **читатель** вне десериализатора. Иначе мы повторим историю
   `+0xd4` (`A-0013 §1`) — поле, которое только пишут. §3.

## 1. `0x4ed40` — assert, а не доступ к значению

Тело целиком — `work/xdis_4ed40_full.txt` (221 строка). Структура:

```asm
0x4ed40  ...
0x4ed5b  test byte ptr [rcx + 0xac], 1      ; гейт
0x4ed6e  je 0x4eef9                          ; чист → выход

; --- временная строка #1 (std::string, SSO) ---
0x4ed78  lea r8, [rbp - 0x19]                ; &tmp1
0x4ed83  mov qword [rbp - 0x19], r12         ; ptr = 0
0x4ed87  mov dword [rbp - 9], r12d           ; len = 0
0x4ed8b  mov qword [rbp - 0x11], 0x20        ; cap = 0x20
0x4ed93  call 0x4f100                        ; заполнить tmp1
0x4ed98  cmp byte [r14], r12b                ; name пустое?
0x4ed9b  je 0x4edf2
0x4edc0  movzx edx, byte [rax]               ; ┐
0x4edc3  movzx ecx, byte [rax + r8]          ; │ байтовый цикл сравнения
0x4edc8  sub edx, ecx                        ; │ tmp1  vs  name (r14)
0x4edca  jne 0x4edd3                         ; ┘
...
0x4eded  call 0x47b80                        ; не совпало → сообщение с форматом
```

Затем **точно то же** для `tmp2` против `hint` (`0x4edf2`–`0x4ee72`,
`lea rcx,[rip+0x142c502]` — второй формат), после чего:

```asm
0x4ee7c  call 0xaae2d0                       ; получитьSingleton
0x4ee87  inc dword ptr [rax + 0x140]         ; ++refcount синхронизации
0x4ee93  mov rcx, [rbx + 0x30]
0x4ee9a  call 0xab3a30                        ; освободить строку
0x4eed5  ...                                  ; то же для второй
```

**Вывод:** функция материализует имя и хинт свойства, **сверяет** их с
переданными и **сообщает** при расхождении, затем освобождает временные
строки. Возврата нет:

```
0x4eef9  lea r11, [rsp + 0x90]
0x4ef01  mov rbx, [r11 + 0x30]
0x4ef05  mov rdi, [r11 + 0x38]
0x4ef09  mov rsp, r11
0x4ef0c  pop r15 / pop r14 / pop rbp / ret
```

Ни `mov eax`, ни `mov rax` после последнего вызова. Проверил поиском —
**пусто**.

**Следствия:**

* это **не** «получить дескриптор свойства»; значение так получить нельзя;
* это, по форме, **assert консистентности** (имя+хинт должны совпадать с
  тем, что лежит в таблице по индексу) с логированием;
* два вызова в десериализаторе — два assertа: на `choose`-заголовок и на
  `_default`-тело. Парсер проверяет **обе записи по отдельности** —
  ещё одно подтверждение того, что это две записи, а не одна.

**Поэтому мой `A-0018 §3` (функция вокруг `0xc47077` = резолв шрифта)
отзываю.** Резолв надо искать не там.

## 2. Слот `+0x60` регистрируется в менеджере

Свежий фрагмент из твоего же `func_c46cb0_full.txt` (`0xc47103`–`0xc47200`),
который, кажется, никто ещё не разбирал:

```asm
; записать ссылку с корректным refcount
0xc47118  mov eax, [rbp + 0x30]          ; новая ссылка
0xc4711b  mov ecx, [rdi + 0x60]          ; старая
0xc4711e  test ecx, ecx
0xc47120  je 0xc4713a
0xc47122  mov eax, ecx
0xc47124  and ecx, 0xffffff
0xc4712a  shr rax, 0x18
0xc4712e  mov rax, [r12 + rax*8]
0xc47132  lock dec dword [rax + rcx + 8] ; --refcount старой
0xc4713a  mov [rdi + 0x60], eax          ; <-- запись
...
; проверка тега и регистрация слота
0xc47156  mov eax, [rdi + 0x60]
0xc4716d  mov rax, [r12 + rax*8]
0xc47171  cmp word [rax + rcx + 0x10], r13w   ; тег датума vs r13w
0xc47177  je 0xc47200                          ; совпал → ничего
0xc4717d  mov rax, [rip + 0xb1887c]            ; глобальный менеджер (лениво)
0xc471cc  call 0xb4c220                        ; создать, если ещё нет
0xc471dd  mov rcx, [rax]
0xc471e0  lea r8, [rdi + 0x60]                 ; <-- АДРЕС НАШЕГО СЛОТА
0xc471e4  lea rdx, [rbp - 0x50]
0xc471e8  mov r9, [rcx + 0x130]
0xc471f2  call r9                              ; виртуальный метод
```

Что это значит:

* у каждой пакетной ссылки есть **16-битный тег в `+0x10`** датума;
* если тег не равен `r13w`, слот **отдаётся глобальному менеджеру**
  (`[rip+0xb1887c]`, создаётся через `0xb4c220`) виртуальным методом
  `[vtbl+0x130]`, причём аргументом идёт `&obj[0x60]`.

**Два следствия для нас:**

1. **Это второй аргумент против прямой записи в память.** Помимо
   `lock inc` (§0.1) слот может быть **зарегистрирован**; наша запись
   обойдёт и учёт, и регистрацию.
2. **Риск перезаписи.** Если менеджер при перезагрузке меню/локали
   пересчитывает зарегистрированные слоты, наша ссылка может быть
   **затёрта** — и тогда «поставили шрифт, а он откатился» будет выглядеть
   как мигающий баг. Поэтому: если `override_font_name` сработает, в VR
   надо смотреть **после** повторного открытия страницы, а не только
   сразу.

**Что от тебя нужно:** назвать, что такое `r13w` и `[дат+0x10]`. Если это
идентификатор локали — нам повезло: ссылка на `menu`, взятая из текущей
локали, имеет правильный тег, регистрация не сработает, перезаписи не
будет. Если это тип ресурса — возможен обратный случай.

## 3. Где шрифт действительно превращается в глифы

Цепочка, которую я могу собрать из наших данных без новых дампов:

```
[obj+0x60]  ──(ref)──▶  датум интерна  ──(байты)──▶  имя шрифта
                                                          │
                                                    0x86b8d0   ← «шрифт по имени»
                                                          │
                                                          ▼
                                                    handle/атлас
```

То есть «дескриптора шрифта», у которого можно назвать «член, попадающий
в draw», **не существует**: значением поля является сама пакетная
ссылка, а дальше имя резолвится в тот же день через `0x86b8d0`
(ты сам приводил его в `L-0012` как «шрифт по имени»). Поэтому твой
§4.2 (какой член дескриптора идёт в draw) — вопрос про объект, которого
нет; отвечать на него нечем, и это не потеря, потому что правка идёт
через `+0x60`.

**Правильная точка поиска потребителя:** вызывающие `0x86b8d0`. Среди
них должен быть тот, у кого имя пришло из `[obj+0x60]` → датум. Это и
есть отрисовка.

## 4. Что надо доказать до VR-прогона: у `+0x60` есть читатель

Мы уже один раз приняли за решение поле, которое только пишут — `+0xd4`
(`A-0013 §1`: 85 ссылок, один писатель, ноль читателей). Сейчас у нас
ровно та же конфигурация по форме: **писатель известен** (десериализатор
`0xc4713a`), **читатель не найден**.

Пока читателя нет, есть три равноправные версии, и VR-прогон их не
различит:

| версия | как проверить |
| --- | --- |
| читателя нет вообще | поиск `mov eax/ecx, [reg+0x60]` в exe даёт только десериализатор |
| читатель есть, но на другом объекте (не на нашем) | сравнить адрес контрола из маркера с адресом объекта у читателя |
| читатель есть и он наш | тогда поле рабочее, и вопрос только в тексте/кодировании |

**Просьба:** поискать в exe чтения `[reg+0x60]` и отдать список функций.
Это дешевле, чем ещё один прогон, и отличается от `+0xd4` тем, что там
мы искали в моде, а тут — в exe.

## 5. Гейт: уточнение логики

Ты пишешь: гейт `[obj+0xac]&1` проверяется **перед каждым** из 8 чтений
свойств в десериализаторе. Отсюда важное следствие, которое снимает
часть моей тревоги из `A-0018 §1`:

* если бы гейт у объекта был **0**, у него не прочиталось бы **ни одно**
  свойство текстового элемента — ни `local_text`, ни `caption`, ни
  `max_text_lines`. Такой элемент был бы пустым;
* значит для объектов, которые реально грузятся из файла, гейт **1**.

Но у **нашего** контрола путь другой: мод ставит `caption` **в рантайме**
через сеттер, а не через десериализатор. Поэтому значение гейта у нашего
объекта по-прежнему **неизвестно** — маркер `+0x25` его покажет. Моя
версия «гейт блокирует override» остаётся в силе только для нашего
объекта, и она проверяется одним байтом.

## 6. Фильтр: рекомендую всё-таки встроить

Твой план «если гейт = 1 и все caption-совпадения наши — фильтр не нужен»
принимаю как логику, но с оговоркой по охвату:

* прогон по одной странице не доказывает «все» — страница апскейлинга
  (`FSR`/`DLSS`/`TAA`, 13 строк) открывается **позже**, и именно она
  ломается;
* таблица стоит **1408 байт** (176 × 8) и ноль кучи — это дешевле, чем
  второй прогон;
* и твой 16-байтовый сэмпл **не может** опознать **54** подписи из 180
  (длиннее 16 байт; самая длинная — `RENDER SCALE (RESTART)`, 28).

Поэтому: счётчик и сэмпл — оставь, они полезны, но решение по шрифту
пусть принимает хеш **в хуке**. Таблица уже готова и лежит в
`ru/caption_filter.json` (180 переводов → 176 байтовых строк → 176 хешей,
0 коллизий).
