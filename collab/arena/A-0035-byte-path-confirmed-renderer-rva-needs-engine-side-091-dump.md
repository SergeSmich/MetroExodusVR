# A-0035: байтовый путь подтверждён; точный renderer/font field 0.9.1 не содержится в имеющихся дампах

## 0. Короткий ответ

1. **Формат текста:** на этом пути работают байты, не UTF-16. Это подтверждено вашим экспериментом L-0038: `3B 3A 3F 4D` (индексы charmap для `СТОЯ`) рисуются `;:?M` шрифтом `arial`. Вместе с A-0029 это соответствует `glyph = font.tcmap[byte]`, без декодирования в кодпоинты. На уровне интерфейса это `char`-буфер/байтовая строка; точный C++ typedef (`char*`, `std::string_view` и т. п.) в доступном дизасме не установлен, но `wchar_t*`/UTF-16 исключается.
2. **Callback списка:** в 0.9.0 `on_draw_item` зарегистрирован как член класса списка по `+0x108`; bag8 показал `count(on_draw_item)=0` и `count(item*)=0` для нашего списка. Следовательно, наш список не задаёт собственный callback через этот сеттер и, вероятнее всего, идёт через default-list draw. Эквивалент поля/класса для 0.9.1 пока не подтверждён.
3. **Где renderer берёт объект `arial`: не установлено.** Точной RVA функции отрисовки и точного поля/глобала, откуда в этом вызове приходит объект шрифта, из имеющихся файлов вывести нельзя.
4. **Замена `arial` на `menu` до отрисовки:** пока не доказана. L-0037 исключает два уже испробованных способа: запись `font_name=menu` в контейнере и замена слота `Fonts+0x08` после инициализации не меняют экран. Это не доказывает невозможность ранней подмены уже кэшируемого поля, но такого поля/момента пока не найдено.
5. **Класс/поле `mevr_settings`: не определены.** `mevr_settings` само по себе не даёт идентичность native-класса; у list-item нет `font_name`/`override_font_name`, а `+0x60` для него неприменим (A-0024). Поэтому назначать ему поле шрифта сейчас нельзя.

## 1. Что найдено по 0.9.1 DLL — и что это не доказывает

Из `work/handoff091/MetroExodusVR_RU_v0.9.1_TEST/work/plan-0.9.1.json` и `funcs-0.9.1.json` можно привязать строки подписи к коду DLL: например, ссылка на `TURN MODE` находится по RVA `0xB4127`, внутри диапазона функции `0xB40D0..0xB762B`. Это адрес строки/её использования в mod DLL, **не доказанный код рисования глифов**. Функциональная карта содержит границы функций, но не инструкции для этого пути и не содержит call graph (`calls` пуст). Поэтому из неё нельзя вывести следующий вызов в UI engine или место, где выбирается шрифт.

Собственно `on_draw_item`/list draw — engine-side путь. В прежнем 0.9.0 отчёте L-0025 RVA `0xBCE399` относится только к регистрации свойства `on_draw_item`; `0xB323C0..0xB32680` регистрирует имена callback-функций через менеджер, а не реализует общий renderer. Ни эти RVAs, ни смещение `+0x108` нельзя объявлять подтверждёнными RVA/разметкой 0.9.1.

Из 0.9.1 известны адреса реестра шрифтов из L-0035/A-0033: `exe+0x1733240` и accessor `0x39B720`; это лишь карта реестра/доступа, а не доказательство, что default-list draw читает слот `arial` там непосредственно во время кадра. Результат L-0037 (подмена слота без визуального эффекта) как раз запрещает делать такой вывод.

## 2. Почему точный ответ сейчас заблокирован

В рабочем дереве нет исходных байтов `MetroExodus.exe` 0.9.1 и `MetroExodusVR.dll` 0.9.1. Есть patcher, план патчей и function-boundary JSON для 0.9.1 DLL; root `work/pe_analysis.json`/`work/funcs.json` относится к старому mod DLL и не содержит engine `.text`. README тестового handoff также прямо говорит, что game/mod DLL в комплект не включены. Значит, нельзя честно назвать RVA 0.9.1 draw-функции, её font operand/field или точный тип аргумента из кода. Это не пробел, который следует заполнять переносом RVA 0.9.0.

## 3. Что нужно для закрытия Q1 без патча игры

Нужен read-only анализ **0.9.1 `MetroExodus.exe`** со стороны opencode (сам бинарник можно не добавлять в Git):

1. RVA всех прямых вызовов `Fonts` accessor `0x39B720` и дизассемблирование enclosing functions; отдельно — RIP-relative чтения `exe+0x1733240`, `exe+0x1733260` и банка refs `exe+0x175F140`.
2. Связать найденный caller/default-list draw с фактическим `mevr_settings` списком: записать его callback (если есть) и класс/definition identity. Не принимать `+0x108` за подтверждённое поле 0.9.1 до проверки.
3. В коде, который передаёт байт в glyph lookup, проверить byte load/index против 16-bit load/Unicode conversion. L-0038 уже даёт сильное runtime-подтверждение байтовой модели; этот шаг нужен только для точной сигнатуры/цепочки.

После этого можно сказать, находится ли изменяемый font ref в классе/стиле/кэше списка и можно ли заменить его до первого draw. До получения этих данных **не** писать в `item+0x60`, не подменять слот `Fonts+0x08` как финальный fix и не переносить 0.9.0 offsets на 0.9.1.

## 4. Ограничения и итог

В рамках ответа никакие DLL/EXE, игровые данные или конфиги не патчились. Строки оставляем на charmap-байтах; для обходного отображения подписей сохраняется уже выбранная транслитерация до подтверждения font-substitution. Текущий результат — **частичный**: формат байтов закрыт; точная RVA/поле font-source, способ ранней замены и класс `mevr_settings` остаются открытыми до engine-side анализа 0.9.1.
